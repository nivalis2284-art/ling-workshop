# 调试：怎么找根因、怎么体面收场

## 它是什么

调试 = 在故障面前按「科学方法」办事：先立假设、再验证、一次只动一个变量，最终找到**根因**，而不是把症状按下去。

**默认做法 + 理由**：凭直觉乱试「看起来像的地方」，往往把水搅得更浑；按假设检验走，每一步都在排除可能性——即使没修好，也知道排除了什么。

## 什么时候用

- 排查 bug、失败、异常行为时；
- 修复尝试反复不奏效、感觉在原地打转时；
- 决定「要不要换新会话重来」时。

## 所有者是报告者，AI 是调查者

- 该问所有者的：期望发生什么、实际发生了什么、看到过什么报错、什么时候开始的；
- 不该问的：原因是什么、哪个文件有问题、该怎么修——那是调查者的活；
- 对自己写的代码尤其当心：记忆里是「意图」，代码行为才是事实。把自己的代码当陌生人写的来读。

## 假设要「可被证伪」

- 反例（没用的假设）：「状态哪里不对」「时序有问题」——没法验证对错；
- 正例（能用的假设）：「组件因路由切换被重挂载，所以状态被重置」——能设计实验证明它对 / 错；
- 一次只改一个变量：改一处 → 跑 → 看 → 记录，再走下一步；
- 开始前至少列 3 个候选假设，别爱上第一个猜测。

## 常用技法（挑合适的用）

| 技法 | 什么时候用 |
|---|---|
| 最小复现 | 系统复杂、因素太多：把出问题的部分抽出来，一样样删，删到不能再删 |
| 逆推 | 知道正确结果但拿不到：从输出往回推，看哪一环开始不对 |
| 差分 | 「以前好好的，现在坏了」：找出变化的东西（代码 / 环境 / 数据 / 配置） |
| 二分 | 范围大（大量文件 / 大量提交）：从中间切，判断问题在前半还是后半 |
| 完整读 | 别只扫「看起来相关」的行——把函数整段读完，问题常在你没看的那半句 |

## 常见思维陷阱

| 陷阱 | 表现 | 解药 |
|---|---|---|
| 确认偏误 | 只找支持自己猜测的证据 | 主动找能推翻它的证据 |
| 锚定 | 第一个解释扎了根 | 先列 3 个假设再动手 |
| 可得性 | 拿最近的 bug 套这次的 | 每个 bug 当新的查 |
| 沉没成本 | 「都查两小时了，继续查」 | 每半小时自查：换条路会不会更快 |

## 收场规则（什么时候停）

出现这些情况 → 停下当前思路：

- 连续 3 次修复尝试都无效；
- 说不清现在的行为为什么是这样（别在不懂的地基上继续加改动）；
- 「修好了，但不知道为什么会好」——那是运气，不是修复。

停止后动作：

1. 写清三样：**已确认的事实 / 已排除的假设 / 新假设**；
2. 涉及跨会话 → 写进 `docs/交接.md` 的「已试与假设」一节（见 `.agents/skills/handoff/SKILL.md`）；
3. 建议换新会话——新上下文常能一眼看到旧上下文看不见的答案。

## 检查清单

- [ ] 问的是体验，不是原因（该问所有者的话问对了）
- [ ] 列了至少 3 个可证伪的假设；一次只动一个变量
- [ ] 每一步实验有记录（试了什么、学到什么）
- [ ] 修复后验证：复现不出、相关功能没坏、边界情况看过
- [ ] 若触发停止规则：三样写清、换会话建议已给
