# 执行：怎么做、怎么停

## 它是什么

执行 = 按「已确认的计划」逐步实施：每个任务走完「做 → 验证 → 提交 → 回读确认」，遇到问题按规则处置。目标是：任何时刻中断，产出都可追溯、可恢复。

**默认做法 + 理由**：这条循环看着慢，但「做到哪了」永远能从 git 里查出来——宁可小步慢跑，不要大段冲刺之后说不清。

## 什么时候用

- 计划经所有者确认后，开始实施时；
- 执行中途遇到故障、偏差，或拿不准要不要请示时。

## 核心循环（每个任务）

1. **做**：只动计划里写明的东西。顺手发现的其他问题先记下、不顺手修（那属于「偏差」，见下节）。
   上下文纪律：先搜索定位再读，只读与当前任务相关的文件；不整篇盲读。
2. **验证**：跑计划里该任务的验证（测试 / 命令 / 实测）。不过关就不提交——先修复，或按偏差规则处置。
3. **提交**：一个任务（或一个能独立说清的小块）一次提交；提交信息写清「改了什么、为什么」。
4. **回读确认**：提交后回读 `git log -1` 与 `git status`，确认提交真的落盘、内容对得上。
   为什么：没核对过的提交等于没发生——看似提交了，实际可能什么都没发生。

（同时遵守 `AGENTS.md` §四：频繁提交、逐笔推送。）

## 偏差处置（计划之外的事）

执行中发现计划没写的事，按四档处理：

| 档 | 情形 | 处置 |
|---|---|---|
| 1 | 小毛病（明确的 bug、错字、笔误级修正） | 顺手修好，记入提交信息 |
| 2 | 关键缺失（不做会导致功能不正确 / 不安全） | 补上并加验证，记录 |
| 3 | 阻塞（环境、依赖、路径问题挡住去路） | 解除阻塞后继续，记录 |
| 4 | 架构级 / 影响范围大（改结构、换方案、动边界） | **停下，请示所有者**；不自行决定 |

拿不准算第几档 → 按第 4 档处理（请示）。

## 什么时候必须停下请示

- 要改计划范围之外的东西（尤其第 4 档）；
- 需要人工操作（密钥、外部账号、只有所有者能做的事）；
- 需要肉眼 / 手感验收（界面效果、交互体感）；
- 计划里明确标了「等所有者确认」的点。

反向规则：**能自动完成的尽量自动完成**——请示只留给「做不了」和「不该做主」的事。

## 失败与打转

- 同一问题连续尝试 3 次仍无果 → 停下。写清三样：**已确认的事实 / 已排除的假设 / 新假设**，再决定继续或换新会话（见 `.agents/skills/debug/SKILL.md`）。
- 「修好了，但说不清为什么好」——视为未修好，继续查（运气不是修复）。

## 收尾

- 全部任务完成、验证通过 → 转独立复核（见 `.agents/skills/review/SKILL.md`）；
- 若属里程碑阶段：更新 `docs/里程碑/当前里程碑.md` 阶段表（状态 + 提交号）。

## 检查清单

- [ ] 每个任务：先验证后提交、提交后回读确认
- [ ] 提交信息写清「改了什么、为什么」
- [ ] 偏差按四档处置；第 4 档已停下请示
- [ ] 没有「顺手多做」的范围外改动
- [ ] 连续失败 3 次时已停下写状态
