# 里程碑：怎么建、怎么拆、怎么归档

## 它是什么

里程碑 = 一块能独立说清「完成了什么」的大工作（例：首版与第一部分改造、加回第二部分）。它同时是**开发历史记录的载体**：每个里程碑完成后整包归档，`docs/里程碑/已完成里程碑/` 就是项目的开发史。

## 新建里程碑（流程）

1. 与所有者一起定四样：
   - **名字**：短、可归档（如「首版与第一部分改造」）；
   - **目标**：一句话；
   - **必须达成**：可验证的清单——完成时逐条核对的就是它；
   - **锦上添花**（可选）：不达标不影响完成。
2. 建议**阶段拆分**（原则见下），呈给所有者确认；
3. 写入 `docs/里程碑/当前里程碑.md`（目标 / 阶段表 / 决策记录）。

## 当前里程碑的格式（`docs/里程碑/当前里程碑.md`）

```markdown
# 当前里程碑

## 目标
（一句话 + 必须达成：可验证的清单）

## 阶段表
| 阶段 | 内容 | 状态 | 提交 |
|---|---|---|---|
| 阶段1-短名 | 一句话 | 未开始 / 进行中 / 完成 | 提交号 |

## 决策记录
（所有者拍板的重要决策，逐条：决定 + 原因）
```

## 阶段怎么拆（四原则）

1. **垂直切片优先**：每个阶段交付一条完整可验收的能力路径，而不是「先做完全部 A 层、再做 B 层」。
2. **每阶段可独立验收**：结束时能拿出证据（测试通过 / 功能实测）。
3. **依赖显式**：写清前置。
4. **粒度参考**：一个阶段 3–7 件能独立说清的事；过大先拆，过小可合并。

## 阶段调整（增 / 插 / 删）

- 需要增、插、删阶段时：先向所有者说明「为什么」，同意后改阶段表；
- 每次调整在决策记录（或提交信息）里留一笔——阶段表永远与事实一致。

## 更新规则

- 阶段开始 / 完成时，更新阶段表（状态 + 提交号）；
- 所有者拍板的决策，随手记入决策记录；
- 一个里程碑同一时间只进行一个阶段。

## 完成前审计

进入归档之前先审计一轮：

- 逐条核对「必须达成」——每条要有证据（测试输出 / 实测 / 文件路径），不许凭感觉打勾；
- 扫一遍缺口：承诺了没做的、建了没接线的；
- 有缺口 → 不开归档流程，先转新计划补齐（见 `.agents/skills/plan/SKILL.md`），补完再审。

## 完成与归档（动作序列）

里程碑完成时，按顺序执行：

1. **验证**：逐条核对「必须达成」，全部成立才算完成（即上节审计）；
2. **打标签**：`git tag <里程碑名>`（让代码可回到这个点）；
3. **收包**：把 `当前里程碑.md` + `docs/计划/历史计划/` 全部 + `docs/审查记录/历史审查记录/` 全部，移入 `docs/里程碑/已完成里程碑/<里程碑名>/`；
4. **清洁**：各文件夹回到「只留最新 / 空」状态；
5. **刷新**：更新 `docs/地图.md` 的「当前状态」一节；
6. **开新**：重建空的 `当前里程碑.md`。

## 检查清单

- [ ] 阶段表状态与提交号保持最新
- [ ] 阶段调整都经所有者同意并留痕
- [ ] 归档前审计通过（必须达成逐条有证据）
- [ ] 归档动作按序完成（标签 / 收包 / 清洁 / 刷新 / 开新）
