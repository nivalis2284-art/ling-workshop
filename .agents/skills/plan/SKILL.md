# 计划：怎么写、怎么归档

## 它是什么

计划是**执行前的契约**：开工前写、经所有者确认后执行。它只描述「这一步怎么做、怎么算做完」。

**一句话原则（来自 GSD）：计划就是给 AI 的提示词。** 计划写得模糊，产出就会模糊——每个任务都要具体到「拿着它就能直接动手」。

## 计划前（先对齐，再动笔）

1. **讨论**：范围、方案取舍、依赖里拿不准的地方 → 向所有者提问对齐（不要替他拍板）；重要决定写进计划「依据」一节。
2. **调研分级**（按任务性质选深度，别过也别欠）：
   - 0 级：纯内部改动、有既有惯例 → 跳过调研；
   - 1 级：确认一个已知库的用法、低风险小决定 → 快速查证（几分钟）；
   - 2 级：在多个方案间选择、接新外部服务 → 标准调研，结论写进「依据」；
   - 3 级：影响长期架构、无现成模式 → 深度调研后再设计划。

## 格式骨架（`docs/计划/计划.md`）

```markdown
# 阶段计划：<短名>

> 日期 ｜ 状态：待确认 / 已确认 / 已完成 ｜ 所属里程碑

## 目标
（一句话；完成时什么必须为真）

## 依据
（为什么做、源自哪里；讨论与调研的结论）

## 改什么（范围清单）
（逐条列文件 / 模块级改动）

## 不改什么（边界）
（显式列出本次不动的东西）

## 执行步骤（任务清单）
每个任务写全四要素——缺了它就是「模糊计划」，产出也会模糊：

### 任务 1：<名称>
- 文件：（精确路径）
- 做法：（具体做什么；不写「实现 X」这类空话）
- 验证：（怎么验：命令 / 操作）
- 完成标准：（可机械对照）

### 任务 2：…

## 验收标准
- [ ]（可机械对照）
- [ ]

## 风险与回退
（恢复点 / 出问题如何撤销）
```

## 写法要求

- **路径精确**：写清具体文件，不写「相关文件」。
- **验收可对照**：每条能打勾；不写「功能正常」这类无法验收的话。
- **不写代码级细节**：细节属于执行阶段。
- **「不改什么」必须非空**：最常见的失控不是做错，而是顺手多做。
- 计划里不写长期「必须 / 禁止」式限制（需求不是限制，见 `AGENTS.md`）。

## 完稿自检（写完先自己过一遍）

- [ ] **覆盖**：每个需求 / 目标都有任务承接，没有「没人管」的部分
- [ ] **完整**：每个任务四要素（文件 / 做法 / 验证 / 完成标准）写全
- [ ] **顺序**：任务依赖排对，先做的排前面
- [ ] **接线**：新做的东西有「被用起来」的安排（建了要接入，不只是建）
- [ ] **粒度**：单个任务别大到说不清；大到要拆就拆
- [ ] **验收**：验收标准能机械对照（不是「感觉好了」）

## 归档

- 进入下一阶段时：旧计划**改名**（`计划-<里程碑>-<阶段>.md`）移入 `docs/计划/历史计划/`（不存在则创建）。
- 里程碑完成时：`历史计划/` 全部随包收进里程碑档案（见 `.agents/skills/milestone/SKILL.md`）。
- `docs/计划/计划.md` 永远只留「当前一份」。
