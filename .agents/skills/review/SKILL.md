# 审查：怎么查、怎么写

## 它是什么

审查 = **独立于执行者的复核**：对照计划的验收标准，逐条验证「是否真的完成」，并留下证据。

**为什么强调「独立」**：看着东西被做出来的上下文，天然相信它没问题；换一套上下文（新会话 / 子代理）复核，才查得出「执行者以为做完了」的漏洞。

## 什么时候用

- 一轮工作 / 一个阶段完成后的独立复核；
- 撰写审查记录、归档旧审查记录时。

## 三级验证（核心方法）

对每个「已完成」的声明，逐级问：

1. **存在**：文件 / 功能真的在吗？（不是只在计划里）
2. **实质**：是真实现，不是空壳？（TODO / placeholder / 空函数 = 未完成）
3. **接线**：真的被调用 / 被装配 / 被使用了？（建了文件没接入 = 没完成）

绝大多数「做完了但没生效」的问题死在第 3 级。

## 证据制（没证据不算通过）

| 声明 | 需要的证据 |
|---|---|
| 「测试通过」 | 实际测试输出 |
| 「功能可用」 | 实测步骤 + 看到的结果 |
| 「接口 / 命令工作」 | 命令 + 返回内容 |
| 「文件已建」 | 路径 + 内容抽查 |
| 「界面正常」 | 截图，或列入「请所有者确认」 |

禁语：「应该能用」「看起来对」「以前类似这么做」——不能作为通过依据。

## 主动扫描（别只看执行者说做了什么）

动手扫一遍存根迹象，命中即登记：

- TODO / FIXME / XXX / HACK 注释；
- 占位内容：placeholder、「coming soon」、空函数、空返回；
- 只打日志不干活；
- 建了没接线：新文件在别处没有任何引用 / 调用。

## 需要人工验证的事项

AI 验不了的（视觉效果、手感、真实环境行为）：不许跳过、不许代替所有者点头——列成清单交给他确认：

（在审查记录里加「请所有者确认」一节：做什么 → 期望看到什么 → 为什么需要人工。）

## 格式骨架（`docs/审查记录/审查.md`）

```markdown
# 审查记录：<对象，如 阶段N>

> 审查对象：<计划链接> ｜ 日期 ｜ 复核方式（独立于执行者）

## 验收项对照
| 验收标准 | 结果 | 证据 |
|---|---|---|
| （逐条） | 通过 / 不通过 | （命令输出、数字、文件路径） |

## 发现的问题
（分级：阻断——不修不能收 ／ 一般——该修、可带着走 ／ 建议）

## 请所有者确认
（需要肉眼 / 手感验收的事项；没有则写「无」）

## 结论
通过 / 有条件通过 / 驳回

## 回退点
（若有）
```

## 写法要求

- **贴证据**：命令与输出、数字、文件路径。不写「看起来没问题」。
- 没通过就不写「通过」；不确定标 `unknown`。
- 主动搜一遍存根迹象（见上节扫描清单），命中即登记。

## 不过怎么办（缺口 → 转计划）

- 缺口逐条列清：什么没达标、缺什么才达标；
- 转新计划修复（见 `.agents/skills/plan/SKILL.md`）——不要在审查记录里直接开修；
- 修完对缺口重审；上轮通过的项做快速回归即可。

## 归档

- 新一轮开始时：旧审查**改名**（`审查-<里程碑>-<阶段>.md`）移入 `docs/审查记录/历史审查记录/`。
- 里程碑完成时：随包收进里程碑档案（见 `.agents/skills/milestone/SKILL.md`）。
