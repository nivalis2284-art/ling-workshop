# 审查：证据优先，记录有归宿

## 审查方法

根据风险自行选择代码检查、测试、真实环境验证及独立视角；不用每次小改动都启动子代理。核查功能是否**存在、真实实现、接入运行路径、符合需求**，以及数据和权限边界是否安全。

结论明确区分**通过、失败、未验证、需所有者体验确认**。不通过删除测试、弱化断言或仅凭模型主观感觉宣布通过。发现缺陷后在已授权范围内可直接修复并复验，不必为了流程另起计划。

## 正式审查文件与格式

- 当前阶段或当前审查对象：`docs/审查记录/审查.md`，**仅保留最新一份**。
- 新一轮正式审查替换旧审查时，**先将旧审查改名归入 `docs/审查记录/历史审查记录/`**，名称标明里程碑、阶段或对象；不得直接覆盖旧结论。
- 小任务没有独立审查留档价值时，可在提交或交付说明中记验证，不强行新建 `审查.md`。

正式审查用 Markdown，至少包含：

1. 标题、对象、日期、方式/范围；
2. **结论**与验收项状态；
3. **关键证据**：实际执行的命令、结果、链接或文件路径；
4. **缺口与风险**：失败、未知、跳过的测试；
5. **需用户确认的事项**（如有）；
6. 回退点或恢复提示（如相关）。

历史审查记录应随里程碑整包归档。保留原始结论，修正后可追加说明或创建新轮审查，不能倒改历史为“全部通过”。
