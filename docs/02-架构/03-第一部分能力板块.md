## 一、判断标准

采用"最小 harness"的一条通用标准：

> **去掉它，Agent 是完全不能跑，还是只是跑得没那么好？**
> - 完全不能跑 → **核心组件**（属第一部分）
> - 只是跑得没那么好 → **辅助组件**（建议保留可拆除性）

配套四条设计原则：**极简性**（能不加就不加）、**可拆卸性**（辅助组件能干净移除，不与核心纠缠）、**模型无关性**（不为某个模型的怪癖做适配）、**面向进化**（为"越跑越好"留出接口）。

背景共识：2023–2026 的 Agent 发展史，本质是"人为控制逻辑不断被模型能力淘汰"的历史。**Harness 里每一行"聪明"的控制逻辑，都是在和未来的模型能力对赌。** 所以凡是"模型迟早自己学会"的，都不该写死在系统里。

## 二、逐项判断

### 2.1 Harness 核心六件

| 组件 | 定位 | 现状 | 进第一部分？ | 方向 |
| :--- | :--- | :--- | :--- | :--- |
| **Agent 循环** | 核心中的核心：执行工具 → 捕获结果 → 追加进上下文 → 再次调用模型 | **缺**。对话是一问一答；循环只存在于独立的"任务"路径 | ✅ **核心组件** | 把任务的执行循环下沉为对话本身的循环，取消"聊天"与"任务"两条断头路 |
| **原子化工具** | 模型发起调用的能力通道 | 有，但方向反了：**一堆自定义动作 + 一个跑命令的工具** | ✅ **核心组件** | 反过来：**以低层原语为主**（命令、文件读写、文本编辑、搜索），自定义动作为辅。工具不是越多越好，过多会降低调用准确率 |
| **上下文管理** | 解决"不断累加的消息"与"有限窗口 + 注意力"的矛盾 | 有，但**超预算就整条失败** | ✅ **核心组件** | 从"失败"改为四种手段组合：压缩旧工具结果、必要时摘要、把中间状态写进文件、必要时隔离 |
| **文件系统** | 承担三重角色：工作记忆、执行环境、**隔离边界** | 部分有（沙箱就是第三个角色） | ✅ **核心组件** | 明确三重角色。前两个角色现在几乎没用起来——中间状态应该能落盘，而不是全堆在上下文里 |
| **Hooks** | **机制与策略分离**：循环负责推进，钩子负责施加控制 | 无。权限、审计、校验都**硬编码在流程里** | ✅ **核心组件** | 把权限检查、审计、策略从循环里抽出来，通过钩子注入。**这是防止循环长成 if-else 巨兽的关键**，也是消除现有耦合的主要手段 |
| **子代理** | 首先是**上下文隔离**手段，其次才是多 Agent 的起点 | 无 | **暂缓**（先留接口） | 架构上留出“独立上下文的执行单元”的位置；等上下文管理真的吃紧再启用 |

### 2.2 边界组件

| 组件 | 定位 | 判断 |
| :--- | :--- | :--- |
| **技能（Skill）** | **应用层**，不是底层。本质是"能力注册表 + 按需注入说明 + 若干文件"的组合产物 | ✅ **接一半**（见 2.3） |
| **MCP / 插件** | **协议层**，解决"如何连到外部世界"，属加分项而非核心能力 | ✅ **接，作为可选客户端**（见第四节） |
| **长期记忆** | 重要，但**业内无共识形态** | 归长期部分（当前隔离，待加回） |
| **内置计划清单** | 可选，且**易被淘汰**（有主流产品在 2026 年初取消了内置待办工具） | **暂缓**（未来可能追加） |
| **多 Agent 协作** | 扩展形态 | **暂缓**（未来可能追加） |
| **检查点与恢复** | 横切能力，不是独立组件 | 任务路径已有 |

### 2.3 关键区分：技能的两半

这是本次最需要讲清的一处，因为"技能"这个词覆盖了两件性质完全不同的事：

| | **技能作为能力包** | **技能作为长期积累** |
| :--- | :--- | :--- |
| 是什么 | 一个文件夹 + 一份说明文件（含名字、描述、使用步骤、可选脚本与参考资料） | 系统从经历里自己总结出新的技能 |
| 谁产出 | 所有者、第三方、随项目分发 | 系统自己 |
| 需要什么 | 扫描目录、常驻索引、按需加载、执行脚本 | 经历、整理、验证、版本、审批 |
| 归属 | ✅ 第一部分 | 长期部分（待加回） |

**判断理由**：前者去掉之后，Agent 只是"少了别人给它的说明书"，仍然完全能跑；后者去掉之后，Agent 完全不受影响。而后者依赖的正是本次要隔离的那一整套（经历 → 整理 → 自我）。

### 2.4 关键区分：工具的两半

| | **工具的能力通道** | **工具使用的经验改进** |
| :--- | :--- | :--- |
| 是什么 | 模型能发起调用、系统执行并回传结果 | 从过去的成功与失败里改进以后怎么用工具 |
| 归属 | ✅ 第一部分 | 长期部分（待加回） |

## 三、怎么接入（方向）

### 3.1 Agent 循环

- 对话本身就是循环：模型可以请求工具、看到真实结果、继续推进，直到完成或需要用户介入。
- 循环宜**极简**——由模型主导决策，而不是人为预设路径（建议）。
- 策略**建议**经 Hooks 注入而非写进循环体；亦可另寻更优解。

### 3.2 原子化工具

> 取向（当时）：低层原语为主。

- 优先给低层原语（建议）：命令执行、文件读写、文本编辑、搜索——模型最熟悉、可组合性最强。
- 自定义动作从简，低层原语表达不了时再新增。
- 建议每个工具只做一件明确的事（原子性），工具之间不重叠（正交性）。

### 3.3 上下文管理

> 当前档位：截断 + 明确提示。

超出预算就丢掉最老的内容，并**明确说明截掉了什么**。压缩、摘要、中间状态落盘等候选**暂缓**——留到真正需要时再加。

后续如需升级，候选方向：压缩较早的工具结果 → 必要时摘要替换历史 → 把中间状态写进文件按需读回（建议一次只加一档）。

### 3.4 文件系统

明确它同时承担三重角色：

- **工作记忆**：保存计划、中间状态、阶段性结论。
- **执行环境**：承载代码、脚本、输入输出。
- **隔离边界**：限定 Agent 能碰的范围（即沙箱分层的落点）。

### 3.5 Hooks

> 现有事件（三个）：工具调用前、工具调用后、回合结束前。

- **工具调用前**：权限检查、越界拦截。
- **工具调用后**：审计、结果留痕。
- **回合结束前**：将来加回第二部分（记录经历、取上下文）的挂载位，已预留。
- 权限、审计、策略**建议**通过钩子注入而非写进循环体；更多事件按需再扩展。

### 3.6 技能包

> 当前：随项目内置一套基础技能，同时支持扫描外部目录。

按业界已成形的约定接入，**零框架**：

- **形态**：一个文件夹，含一份带元数据（名字 + 描述）的说明文件，可选带参考文档、脚本、模板资源。
- **三级渐进式披露**：
  - 第一级**常驻**：只扫"名字 + 描述"，每个技能约 20–100 token。装几十个技能的成本还不如几张截图。
  - 第二级**按需**：判断任务命中时才读入说明正文。
  - 第三级**自由**：参考文档按需翻，脚本**直接执行**（脚本不是给模型读的，是给模型跑的）。
- **存放位置**：三处——**随项目内置**（开箱即用）、**用户级**（跨项目）、**项目级**（随仓库分发）。启动时扫描并建立轻量索引。
- 内置技能建议保持克制：只放真正通用、不依赖外部服务的（例如文档处理）。
- **安全性**：技能约定本身不含沙箱，安全性依赖宿主已有的权限模型；**技能不给自己扩权**（建议保持此属性）。

## 四、MCP 的现状与接入策略

### 4.1 生态现状（2026 年 10 月）

- 官方注册服务器 **800+**（2026 Q2），含社区目录合计上万。
- 已成为事实标准，主流平台与厂商均有实现。
- 对个人项目而言，**不接等于放弃整个外部能力生态**。

### 4.2 一个必须知道的风险

**2026-07-28 版本是 MCP 发布以来最大的破坏性改版**：

- 协议从"有会话、有初始化握手"改为**无状态、自包含请求**；
- 新增多轮往返请求、统一订阅流、标准请求头、缓存提示、追踪约定；
- 交互界面与长任务被移入可选扩展；
- 部分旧能力进入弃用周期；
- **新旧协议不兼容**，客户端与服务器需要版本协商或双时代实现过渡。

### 4.3 接入策略

> 当前：最小集。

**当前范围（最小核心）：**

| 现在做 | 暂缓（按需再加） |
| :--- | :--- |
| 连接服务器（本地与远程） | 交互界面扩展 |
| 列工具、调工具、回传结果 | 长任务扩展 |
| 协议版本协商 | 多轮往返请求 |
| 结果缓存提示 | 订阅流 |

**理由**：扩展都是"锦上添花"，而版本协商是"能不能连上"的前提。先把最小集做稳，扩展按需再加。

**保留要求（建议）**：MCP 保持**可选连接**——不配任何服务器时，Agent 照常工作；不让它变成新的前置门槛（Docker 那一课的教训）。

## 五、暂缓与保留

**暂缓（未来可能追加）**：

- 内置计划清单：让计划自然产生。
- 多 Agent 协作。
- 子代理：先留位置。
- MCP 扩展（先做最小核心）。

**保留（建议）**：

- MCP 保持可选：不配也能跑。
- 技能不扩权：技能是知识约定，不是权限来源。
