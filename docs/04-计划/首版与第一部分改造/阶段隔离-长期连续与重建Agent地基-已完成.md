## 一、问题：先把「版本必须一致」的来源查清楚

### 1.1 需求原文里它长什么样

翻回 `docs/研究/2026-10-08-阶段讨论记录.md`，这个约束的来源是三句话，全部写在**缓存与上下文**的讨论里：

| 位置 | 原文 | 说的到底是什么 |
| :--- | :--- | :--- |
| 第 799 行 | 「对更新、撤回、编辑分支和重大人格变化建立明确的上下文生效规则；必要时重建受影响部分，**不为保持缓存而继续使用已失效资料**」 | 下一轮**组装上下文**时不要用旧版本 |
| 第 949 行 | 「确认的人格变化和用户纠正**必须及时生效**，必要时使受影响缓存失效，**不能为命中而保留错误**」 | 同上，针对前缀缓存命中率 |
| 第 974 行 | 「用户编辑消息／选定新回复后，**标记**受影响摘要、认识、人格候选及技能依据失效或待重算」 | 动词是「**标记**」，不是「中止」 |

### 1.2 结论：需求没有要求「本轮中止」

三句原话的共同目标是：**不要为了省缓存钱，把过期的人格或记忆继续喂给模型**。这是一个关于「**下一次组装**」的要求。

但现在的实现是：对话回合在开始和结束各核对一次版本，不一致就把**正在生成的这一轮**判为 `context_invalidated` 并整条作废。

从「下一轮别用旧的」到「这一轮必须中止」，中间这一步是**实现层自己加的**，需求里找不到依据。上一轮开发 AI 大概出于两个动机加固了它：

1. 「绝不静默出错」的执念——宁可让用户看到失败，也不要让一条基于旧版本的回复悄悄落库；
2. 并发恐惧——担心「生成到一半状态变了」这种场景没被覆盖。

第 2 条动机，下面第三节会证明它大部分打不到。

## 二、「假想敌」审计：哪些限制其实触发不了

按「真实触发条件 → 今天能否真的触发 → 判断」逐条核对源码。

| # | 限制 | 真实触发条件 | 现在能否触发 | 判断 |
| :-- | :--- | :--- | :--- | :--- |
| 1 | 落库前校验**自我**版本（`self_revision`） | 生成期间你批准了一个候选 / 删了一条身份条目 | **能**。身份页与对话页完全独立，身份页的 `busy` 只表示它自己的请求在跑，它**不知道**对话正在生成 | 真实可达。但正确做法是「标注」而非「作废」 |
| 2 | 落库前校验**记忆**版本（`memory_refs`） | 生成期间改掉或归档一条被引用的记忆 | **几乎不能**。上游 `MemoryMaintenance._check_running` 已经拦住「修改正在被本次对话引用的记忆」 | **假想敌**：上游已拦住，这是重复防线 |
| 3 | 落库前校验**附件摘要** | 附件文件被从磁盘上删掉或改坏 | 极难。附件是只由程序管理的不可变文件，有摘要校验兜底 | **假想敌** |
| 4 | 落库前校验**来源仍有效** | 生成期间删掉某一轮对话（导致来源被标记不可见） | UI 已禁用；只有绕过界面直接调接口才可能 | 半假想敌 |
| 5 | 落库时校验**对话头**（`expected_head`） | 生成期间切换了分支 | UI 已禁用；接口可达 | 半假想敌 |
| 6 | **禁止修改被引用的记忆**（`_check_running`） | 你想在生成期间顺手改一条记忆 | **能** | 真实，但代价是「你被挡住」。应改成标注 |
| 7 | 任务遇到记忆/自我变化就 **blocked** | 后台任务运行期间你改了它引用的资料 | **能**（任务与前台并行） | **真实且重要，建议保留** |
| 8 | 整理结果遇到自我变化就丢弃（`self_changed`） | 整理期间自我版本变了 | 极难。整理与自我变化大多在同一把后台锁下串行 | 假想敌 |
| 9 | 备用模型对整条对话**粘性** | 一次故障后不再切回主模型 | 能，且**没有提示** | 隐藏状态，应修 |

**审计结论**：9 条里，真正有触发路径的只有 1、6、7，其中只有第 7 条（任务侧）值得保留强校验。其余 6 条要么被上游重复拦截，要么只能绕过界面触发。

## 三、隔离范围：哪些属于「长期连续与发展」

### 3.1 要隔离的部分

| 模块 | 职责 |
| :--- | :--- |
| `history/` | 原始经历库（原文、版本、可见性） |
| `memory/` | 事件卡、知识、人工纠错、召回检索 |
| `identity/` | 当前自我状态、候选审批、版本回退、系统指令 |
| `learning/` | 后台整理：把经历变成事件卡 / 知识 / 自我候选 |
| `skills/` | 技能积累与版本 |
| `development/` | 长期目标 |
| `context/recall.py` | 按关键词从记忆里捞线索 |
| `conversations/segments.py` | 主题分段（依赖整理产出，可一并归入） |
| 前端 `identity/` `memory/` `skills/` `sources/` 页面 | 上述能力的界面 |

### 3.2 要保留的 Agent 核心

| 模块 | 职责 |
| :--- | :--- |
| `runtime/` | 对话回合编排、流式事件、主备切换、密钥护栏 |
| `models/` | 三协议原生网关 |
| `conversations/` | 消息链、分支、编辑、删除一轮 |
| `tasks/` | 多步执行循环、检查点、工具派发 |
| `tools/` `actions/` `browser/` | 执行能力与浏览器操作 |
| `content/` | 附件解析 |
| `permissions/` | 目录与网页授权 |
| `configuration/` | 模型连接、主备、凭据缓存 |
| `maintenance/` | 备份、恢复、资产 |
| `observability/` | 用量与费用 |
| `api/` `desktop/` | 对外接口与桌面壳 |
| 前端 `chat/` `tasks/` `overview/` `settings/` `onboarding/` `background/` `activities/` | 保留 |

### 3.3 隔离 ≠ 移除

- **代码**：全部保留，不删文件、不改数据表结构。
- **数据**：数据库里的经历、记忆、自我版本、候选、技能、目标**一条不删**，只停止读写。
- **界面**：隔离态下相关页面隐藏或降为只读，避免你在两套状态之间产生误解。
- **可回退**：开关一切回，行为与今天完全一致。

## 四、接缝设计：把长期能力收成一个端口

### 4.1 现状：Agent 核心与长期系统有四个接触点

| 接触点 | 位置 | 方向 | 现在做的事 |
| :--- | :--- | :--- | :--- |
| ① 取上下文 | `runtime/payload.build_payload` → `context/builder` + `context/recall` | 读 | 把「系统指令 + 当前自我状态」拼进前缀，再捞 4 条回忆参考 |
| ② 记录经历 | `history.add`（由对话落库调用） | 写 | 写入经历库，并**排一条整理任务进队列** |
| ③ 落库前校验 | `runtime/service._complete` → `failover.validate_context` | 校验 | 核对自我版本、记忆版本、来源、附件摘要 |
| ④ 反向阻塞 | `memory/maintenance._check_running` | 校验 | 记忆正被引用时禁止修改 |

整理本身（`learning/worker.py`）已经在后台跑，**天然隔离**，不需要动。

### 4.2 目标：定义 `ContinuityPort`

把 ①②③④ 收进一个端口，Agent 核心只依赖这个端口，不再直接引用长期模块。

```
ContinuityPort
├── context(agent_id, refs) -> ContextPacket
│      返回本轮要发给模型的「规则 + 自我 + 回忆」
├── observe(agent_id, source_ref) -> None
│      记录一条新经历（是否排队整理由实现决定）
├── validate(run) -> ValidationResult
│      返回 ok / warning（而不是抛错中止）
└── guard_memory_edit(agent_id, item) -> GuardResult
       是否允许修改某条记忆
```

### 4.3 两种实现

| 实现 | context | observe | validate | guard_memory_edit |
| :--- | :--- | :--- | :--- | :--- |
| `FullContinuity`（现状） | 指令 + 自我 + 回忆 | 写经历 + 排队整理 | 校验（**改为只记 warning**） | 拦住（**改为只记 warning**） |
| `NullContinuity`（隔离态） | 仅系统指令 + 名字 + 近期原文 | 空操作 | 永远 ok | 永远放行 |

切换方式：一个设置项（例如 `continuity_enabled`），默认沿用当前值，隔离时置 false。**改动集中在组装处，业务模块内部不动。**

### 4.4 端口带来的额外收益

即使不做隔离，这个端口本身也值得做——它把「对话回合」和「长期演化」之间的四条耦合边**收敛到一处**，以后想改哪条边，只需要改一个实现类，不必在四个模块里找。

## 五、隔离态下灵是什么样

- **发给模型的东西**：你写的系统指令 + 名字 + 最近一段原文。**没有回忆参考，没有自我状态清单，没有记忆版本标记。**
- **对话落库**：照常写入消息链，但**不排整理任务**，长期资料完全不动。
- **落库前**：不再有版本校验，回复不会因为你在别处改了东西而作废。
- **任务侧**：**保留**记忆/自我变化的强校验逻辑，但隔离态下这两者不会变，等于自动失效；任务本身照常工作。
- **界面**：记忆页、身份页、技能页、目标页隐藏或只读，避免误操作。

## 六、地基：现在的灵离「正常 Agent」还差什么

隔离完会得到一条干净的对话链，但**还不等于一个正常的 Agent**。核对现状：

| 能力 | 现状 | 缺口 |
| :--- | :--- | :--- |
| 模型网关（三协议、流式、思考） | 已有 | — |
| 消息链、分支、编辑、删除 | 已有 | — |
| 多步执行循环 + 检查点 | 已有，但在 `tasks/` 里，最多 40 步 | 与对话完全分离 |
| 工具派发（文件、命令、Docker、浏览器） | 已有，在任务里 | 同上 |
| 权限与审批 | 已有 | — |
| **对话内调用工具** | **明确不支持**：模型一旦要求调工具，本次直接判失败（`tools_unsupported`） | **核心缺口** |
| **对话内多步循环** | 没有，聊天是一问一答 | **核心缺口** |

**结论**：现在这个项目把 Agent 能力切成了两条互不相通的路径——「聊天」（能说不能做）和「任务」（能做但门槛高、要单独建、要选项目文件夹、要审批）。一个「正常 Agent」应该是**一条统一的循环**：对话即循环，模型可以调工具、看结果、继续，直到完成。

所以「打好地基」的真正含义是：**隔离长期部分 → 把 `tasks/` 的执行循环下沉成对话可用的统一 agent loop**。这两步有先后依赖：先隔离，循环才不会被四条耦合边反复打断。

## 七、分步实施

| 阶段 | 做什么 | 行为变化 | 可回退 |
| :--- | :--- | :--- | :--- |
| **S0 加接缝** | 定义 `ContinuityPort` 与 `FullContinuity`，把 ①②③④ 改为走端口 | **无**（纯重构，行为逐字节一致） | 回退提交即可 |
| **S1 降级校验** | `validate` / `guard_memory_edit` 从「抛错中止」改为「记 warning + 落库标注」 | 回复不再因后台变化作废 | 切回 `FullContinuity` 严格模式 |
| **S2 加隔离开关** | 实现 `NullContinuity`，加设置项，默认关闭（即保持现状） | 无 | 关开关 |
| **S3 界面隔离** | 长期页面在隔离态下隐藏/只读 | 无（开关未开时不变） | 关开关 |
| **S4 补整理** | 切回 `FullContinuity` 时，把隔离期产生的经历补排进整理队列 | 无 | — |
| **S5 统一 agent loop** | 把 `tasks/` 的循环下沉到对话，支持对话内工具调用与多步 | 能力新增 | 保留旧任务路径 |

S0–S2 是关键路径。S5 建议等 S0–S4 稳定后再启动。

## 八、代价与风险（必须写明）

1. **隔离期产生的对话不会进入记忆。** 切回后需要一次「补整理」，把这段时间的经历补进队列。补整理的产出质量取决于当时模型的判断，可能不如实时整理。**这是隔离最真实的代价。**
2. **隔离期的灵不会有成长。** 这是你要的，但要确认你接受。
3. **两套状态并存。** 切回瞬间，「自我」会从隔离前的版本跳到当前版本，中间这段时间它没有参与。需要在界面上给出明确提示，避免你以为它「记得」这段。
4. **任务侧强校验不动。** 隔离态下它自动失效，但切回后它仍然存在。这是有意保留的。
5. **S0 是纯重构，风险最高的一步。** 必须保证行为逐字节一致，靠现有回归测试兜底；如果测试覆盖不足，先补测试再动。

## 九、变更安全性（这次改动的自查项）

按本项目一贯的评判口径，逐项检查：

- **可回退性**：每个阶段一个独立提交，S1/S2 均可通过开关回退，不需要回滚数据。
- **静态护栏**：端口用类型定义约束，`NullContinuity` 与 `FullContinuity` 必须实现同一接口，漏实现会在编译期/类型检查期报错。
- **回归测试**：S0 要求现有后端与前端测试**全部通过且不改断言**；S1 需要新增「后台变化不再作废回复」与「标注仍被写入」两类用例；S2 需要「开关关闭时行为与今天一致」的对照用例。
- **缺陷可描述性**：端口是单一入口，出问题时可定位到「是端口实现的问题，还是 Agent 核心的问题」。
- **修复扩散面**：S1/S2 的改动集中在端口实现与组装处，不扩散到记忆、身份、任务模块内部。
