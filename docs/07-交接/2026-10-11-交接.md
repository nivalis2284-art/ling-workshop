## 四、架构骨架（两条主线）

### 4.1 第一部分 vs 第二部分（这是整个项目的结构性前提）

- **第一部分**（`src/lingnexus/` 除 `part2_retired/`）：可独立运行的 Agent 系统——对话、工具/动作、权限、模型、附件、维护、备份、技能包、MCP。
- **第二部分**（历史/身份/记忆/发展/分段/技能长期积累/活动）：当前不装配、未被第一部分引用。
- 现有测试 `tests/test_boundary_part1.py` 会检查这些模块当前未被装配/引用（当时的实现约定，随开发调整）。
- **因此**：F 阶段的新模块叫 `lingnexus.skillpacks`，**不是** `lingnexus.skills`（后者是第二部分的"技能长期积累"，已归档为 `part2_retired/skills_accumulation.py`）。

### 4.2 对话即循环（C 阶段的核心）

一个对话回合 = 有步数预算的循环：

```
每一步：调模型 → 若请求工具 → 逐个执行（BEFORE_TOOL 钩子 → 派发 → AFTER_TOOL 钩子）
       → 结果回灌 → 下一步；直到模型不再请求工具 或 步数用尽
```

**结构性建议：策略经 Hooks 注入而非写进循环体（亦可另寻更优解）。**

| 钩子 | 挂什么 |
| :--- | :--- |
| `BEFORE_TOOL` | 权限（`permissions/hooks.py::permission_hook`）、副作用实时确认（`runtime/confirmations.py::confirmation_hook`） |
| `AFTER_TOOL` | 观测/记账 |
| `BEFORE_TURN_END` | 回合收尾 |

关键代码：
- 循环本体：`src/lingnexus/runtime/service.py`（`ChatRuntime`）
- 工具声明与派发：`src/lingnexus/actions/dispatch.py`（`ToolDispatcher`）、`actions/catalog.py`（工具目录）、`actions/registry.py`（注册表）
- 两个循环共用同一个派发器：`runtime/scope.py`（`ChatToolScope`）、`tasks/execution.py`（`TaskToolScope`）
- 事件流：`runtime.events(run_id)` 产出 `{id, event, data}`——`started` / `step_started` / `tool_started` / `tool_result` / `paused` / `resumed` / `text` / `thinking` / `usage` / `notice` / `complete` / `error` / `model_switch`

## 五、本轮新增了什么（F 阶段 + E 阶段）

### F-1 技能包 · `src/lingnexus/skillpacks/`

- 形态：一个文件夹 + 一份 `SKILL.md`（YAML 元数据 `name`/`description` + 正文），可选带 `references/`、`scripts/`、`assets/`。
- **三级渐进式披露**：
  1. **常驻**：只把 `name` + `description` 注入请求开头，且**计入请求预算**（不是白送 token）。
  2. **按需**：模型用 `read_skill` 工具读入正文。
  3. **自由**：资源清单随正文返回，供按需读/执行。
- **三处扫描**：项目级 > 用户级 > 内置，同名以更具体者为准并记录被遮蔽者。
- **资源读取受限**：拒绝绝对路径与 `..`，**逐段拒绝任何别名**（symlink / junction / reparse point），只读技能目录内的常规文件。
- 内置两枚克制技能（不依赖外部服务）：`safe-bulk-edit`、`csv-to-markdown-table`。
- 接线：`read_skill` 声明为 `meta` 类工具，经 `ChatToolScope.meta` / `TaskToolScope.meta` 派发，两个循环共用。

### F-2 MCP 最小集 · `src/lingnexus/mcp/`

| 文件 | 职责 |
| :--- | :--- |
| `protocol.py` | JSON-RPC 帧、版本协商（不猜，不匹配即报错）、工具命名 `mcp__<server>__<tool>` |
| `client.py` | `StdioTransport`（子进程 + 后台读线程 + 队列）、`HttpTransport`（标准库 urllib）、`McpConnection`（握手 / `tools/list` / `tools/call`） |
| `service.py` | 配置读取（`settings.mcp.servers`）、懒连接、工具声明与调用 |

- **可选**：未配置时零连接、零工具、零启动开销；配置了但连不上的服务器不贡献工具、也不让回合失败。
- **不扩权**：远端工具声明进**同一注册表/派发器**，因此走**同一条 `BEFORE_TOOL` 钩子**与同一派发路径。
- 参数按服务器自 published schema 校验（`ToolSpec.input_schema` 原样透传），本地只做体积上限。
- 调用后超时/断连如实报 `unknown`（可能已产生副作用，绝不谎报 `failed` 诱发重复副作用）。

## 七、踩过的坑（接手者务必知道）

1. **FastAPI 懒加载路由**：本版本用 `_IncludedRouter`，`app.routes` **不会展开子路由**。断言"路由存在"必须改用 `server.openapi()["paths"]`，否则永远查不到。
2. **Windows 目录联接 ≠ 符号链接**：`stat.S_ISLNK` **看不见** junction / mount point（它们被报成普通目录，reparse tag `0xa0000003`）。判据必须用 `S_ISLNK` **或** `st_file_attributes & 0x400`（`FILE_ATTRIBUTE_REPARSE_POINT`）。唯一真源：`src/lingnexus/tools/_paths.py::is_link`。**F-1 曾因此真实越界读到技能目录外的文件**（证伪已留证）。
3. **`ChatRequest` 的字段是 `message` 不是 `text`**（`runtime/types.py`）。测试里极易写错。
4. **不要对 `src/` 做破坏性操作**：本机执行 `git mv` / `rm -rf` 时曾触发工作区视图异常，表现为 `src/lingnexus/` 整棵"被删"（`git status` 全为 `D`）。**全部内容都在 HEAD 里，可完整恢复**：
   ```bash
   git reset -q -- src/ && git checkout -- src/
   ```
   恢复后务必用**独立命令**（`git status --short -- src/`、跑一次测试）验证落盘。
5. **任务循环是无钩子的旧路径**（`tasks/execution.py`）：把 MCP 塞进它会绕过权限与确认闸门，故**有意不接**。MCP 只接对话循环。
6. **`.workbuddy-ai/` 不入库**（已加进 `.gitignore`）；`.gsd/` 框架残留已删除。

## 八、已知边界与遗留（不是 bug，是明确选择）

1. **MCP 工具当前被权限钩子放行**：`permission_hook` 只对本地路径类工具设限，`mcp__*` 不在受限集合内。远端工具的"授权"完全取决于该服务器自身。**若要限制，应新增一条针对 `mcp__*` 的策略钩子，而不是改循环体。**
2. **旧 `src/lingnexus/skills/` 包仍在**（第二部分的技能长期积累，已被边界测试列为禁区）。F 用新模块 `skillpacks`，**未做归档**——归档操作曾触发工作区异常，故保留原样。
