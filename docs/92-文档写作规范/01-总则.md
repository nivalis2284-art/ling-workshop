# 总则：所有文档的通用合格标准

> 动笔前和完稿后各过一遍。写哪类文档，再去看对应分则。

## 动笔三问

1. **写给谁看？**——未来的 Agent、所有者、使用者？读者决定语言和深度。
2. **回答什么问题？**——一句话说清这份文档的存在理由；说不清的文档不该存在。
3. **怎么算合格？**——写完能列出可对照的检查项；列不出的先补结构再写。

## 硬规则

1. **单一真源**：同一个信息只有一个「家」，其他地方放链接，不复制。
   为什么：复制品会静默过期——改一处漏三处，读者不知道信谁。
2. **只写事实与证据**：命令、数字、链接、实测结果；不写空话与愿望。
   为什么：「尽量优化」这类描述三个月后没人知道做到了没有。
3. **每条规则带理由**：写「必须 X」时，在旁边写「因为 Y」。
   为什么：没有理由的规则会被机械执行到荒谬的场景；有理由的规则才能被正确例外。
4. **暂缓就是暂缓，不写成禁止**：当前不做的事写「暂缓（按需再加）」。
   为什么：把取向写成禁令，未来 Agent 会以为项目铁律不准碰——这是本项目踩过的坑（2026-10 大扫除的由来）。
5. **完成即标注，不搬家**：文档完成后改头部状态行 + 文件名加 `-已完成`，留在原文件夹。
   为什么：搬来搬去会把引用搬断、把文件夹结构搬乱；文件夹按「类型」分，不按「完成度」分。
6. **路径一律相对、旁白视角、序号规则**：见 AGENTS.md §三。
   为什么：仓库要在任何机器上克隆即用；文档是项目资产，不是私人笔记。

## 通用反模式

| 反模式 | 为什么是问题 |
|---|---|
| 把临时决定写成正式结论 | 污染后续 Agent 的理解，被误读为永久约束 |
| 把需求写成禁令 | 未来的开发被「不存在的规矩」吓住 |
| 同一信息抄三遍 | 必然互相矛盾，读者无所适从 |
| 状态变化不更新「现在是什么」类文档 | 文档变成谎言，比没有文档更糟 |
| 规则 / 设计类文档用「你 / 我」人称 | 读者分不清是规则还是叙事（面向使用者的手册除外，见 [`AGENTS.md`](../../AGENTS.md) §三） |
| 长文档不设导航 | AI 读不完，等于没写 |
