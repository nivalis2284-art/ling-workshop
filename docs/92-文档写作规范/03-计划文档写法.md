# 计划文档写法

> 模板：[`../08-模板/02-计划模板.md`](../08-模板/02-计划模板.md)。计划是**执行前的契约**——写清楚才允许开工。

## 结构要求

| 节 | 要求 | 为什么 |
|---|---|---|
| 目标 | 一句话 + 本计划不做什么 | 防止执行中范围蔓延 |
| 依据 | 为什么做、源自哪里（指令 / 调研 / 溯源） | 无依据的计划是拍脑袋 |
| 改什么 | 逐条列文件级改动 | 「范围清单」是审查的对照基线 |
| 不改什么 | 显式边界 | 最常见的失控不是做错，而是顺手多做 |
| 执行步骤 | XML 任务结构（见下） | 让验收能逐条钉到任务 |
| 验收标准 | 每条可机械对照（能打勾） | 「功能正常」无法验收 |
| 风险与回退 | 恢复点 / 如何撤销 | 出问题时不用翻 git 历史猜 |

## 任务四字段

每个任务建议写全四个字段（缺项会让执行者自己猜）：

```xml
<task type="auto">
  <name>短名</name>
  <files>精确/文件/路径.py</files>
  <action>做什么；避免什么，以及为什么</action>
  <verify>证明完成的命令或检查</verify>
  <done>可量化的完成标准</done>
</task>
```

- **files**：精确路径，不写「相关文件」——为什么：模糊路径让执行者自己猜，猜错就是返工。
- **action**：写「避免什么及为什么」——为什么：只写要做什么，执行者会重蹈已知的坑。
- **verify**：可执行的命令——为什么：「应该能用」不是证据。
- **done**：可量化——为什么：无法量化的标准等于没有标准。

## 提交前自检清单

- [ ] 每个任务四字段齐全
- [ ] 验收标准逐条可对照
- [ ] 依赖已显式（前置任务 / 前置阶段）
- [ ] 范围适中（单个计划 2–3 个任务为宜；超过先拆）
- [ ] 「不改什么」非空
- [ ] 每条改动都能追溯到「依据」

## 反模式

| 反模式 | 为什么是问题 |
|---|---|
| 验收标准写「功能正常」 | 无法对照，审查沦为签字 |
| 步骤写「实施认证系统」 | 执行者只能自由发挥，计划失去意义 |
| 没有「不改什么」 | 顺手多做，审查时说不清哪些是计划内的 |
| 计划里写代码级细节 | 计划是契约不是实现；细节属于执行记录 |
