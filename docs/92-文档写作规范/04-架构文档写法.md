# 架构文档写法

> 架构文件夹（[`../02-架构/`](../02-架构/00-README.md)）回答「**现在是什么**」——只写现状。

## 写什么，不写什么

| 进架构文档 | 不进架构文档 |
|---|---|
| 现在有哪些能力 / 模块 / 数据流 | 设计理由（去计划 / 审查记录） |
| 当前技术选型与运行位置 | 方案比较过程（去计划「依据」） |
| 隔离 / 暂缓事项及其状态 | 历史状态（完成后改标注，不搬家） |
| 技术债（位置 + 影响 + 建议） | 临时决定（不配进架构） |

为什么：架构文档混入理由和过程，读者分不清「现在是什么」和「当初怎么想的」；更糟的是理由会随认知过时，而现状不会——把易变的写进架构，架构就不可信了。

## 组件记录四元组

每个代码模块 / 能力板块记录：

1. **用途**：一句话
2. **位置**：路径
3. **依赖**：它调用谁
4. **被谁依赖**：谁调用它

为什么：2 / 3 / 4 是改动影响面的地图——没有它，改一个模块不知道会牵动什么。

## 技术债显式登记

已知的烂摊子、妥协、待统一事项，登记在案：位置 + 影响 + 建议处理方式。

为什么：烂在山里没人知道的债才是真债；显式登记的债至少有机会被排期。

## 隔离 / 暂缓事项的注记规则

凡隔离、暂缓、当前不做的，必须带注记：**「当时的约定 / 取向，随开发调整」**。

为什么：这是本项目用一整轮「限制大扫除」换来的教训——把当时的方案写成铁律，未来 Agent 不敢碰，G 阶段加回能力时每步都要先拆心理障碍。

## 反模式

| 反模式 | 为什么是问题 |
|---|---|
| 设计理由写进架构 | 理由会过时，现状不会；混写让整份文档失信 |
| 过时状态不更新 | 架构文档撒谎，比没有更糟 |
| 组件只写用途不写依赖 | 改动影响面全靠猜 |
| 隔离事项写「永久禁止」 | 把暂缓写成禁令，吓住未来的开发 |
