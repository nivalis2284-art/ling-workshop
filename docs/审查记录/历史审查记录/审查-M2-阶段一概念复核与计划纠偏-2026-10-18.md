# M2 阶段一概念复核：工作分支 Agent 与正式计划纠偏

> 日期：2026-10-18。对象：所有者对“工作分支即子 Agent”的产品澄清、当前正式计划、main@164b7e5 源码。方式：GPT 主 Agent 源码与数据契约核对、DeepSeek Max 独立只读审计。状态：**复核完成；产品代码实施尚未获本轮授权**。

## 一、结论

原计划的总体复用方向正确，但把产品主体错误地拆成了“新增持久身份 → 多个 phase → 每阶段新 conversation”的外层结构。现有 continuity_work_branches 已经绑定独立工作 conversation、目标、fork 背景、来源授权、run、经历根与回归 outbox，应直接作为稳定子 Agent 主体。再增加 subagent_id 既不能增加真实任务理解，也让归档、唤醒和经历关联多了一层不必要的概念。

修订后的主张：

1. branch 是子 Agent 主体，branch ID 就是稳定 ID。
2. 同一个 branch 使用其工作 conversation 作为历史树；conversation、run 都不是身份。
3. 新增 append-only 任务状态修订保存原目标、关键决策、进度、未完成项、已验证事实、未知、来源引用和权限版本。
4. episode 表示一次唤醒或阶段，predecessor 指向上一段；run 通过 episode 归属 branch，继续复用 checkpoint/effect/lease。
5. 归档只关闭 episode，不关闭 branch；同 branch 可以休眠、重启和开启后继 episode/run，旧归档和原文保持不可变。

这不是保留当前终态实现的借口：现有 branch 仍是工作执行体，尚不是完整任务型子 Agent。它缺少任务状态演进、episode 链、指导实际消费状态、重启恢复和归档后唤醒路径。修订计划已经把这些作为 P1/P2 本体闭环，而不是将其转成外层身份迁移。

## 二、原规划中的真实问题与合理抽象

| 项目 | 判断 | 理由 |
|---|---|---|
| 复用 conversation、ChatRuntime、checkpoint/effect/lease、experience/source、outbox | **保留** | 已是真实执行与安全基础，换框架或新建 Harness 不会带来产品连续性 |
| 区分 branch、episode、run、归档 | **保留，但重定义** | 一次运行不等于整个 Agent；分阶段归档不能覆盖历史，需要明确责任层 |
| 新增 subagent_id、父灵身份表、active/dormant/retired 独立身份体系 | **删除** | branch 已经是父灵下的工作主体；ID 连续性本身不是产品连续性 |
| 每个 successor phase 强制新 conversation | **调整** | conversation 是工作历史树；是否重开应由来源与上下文证据决定，不能作为“唤醒”的必要条件 |
| 先完成网络隔离与四档/三档全矩阵再建 Agent 本体 | **调整** | 网络探针不是创建、执行、归档、休眠的最低依赖；双轴权限仍保留为阶段一最终能力，按 P3/P4 集中交付 |
| 暂停、普通回合结束、恢复、休眠、唤醒不同状态 | **保留并加强** | 现状确有混写，不能在实现中宣布已恢复 |

真正的问题是任务理解和经历连续性没有稳定承载，而不是缺少更多身份概念。合理的抽象是任务状态与 episode，不是第二套 Agent。

## 四、完整使用场景

场景：灵创建“实现登录修复并验证”的工作分支，子 Agent 独立执行；中途用户增加“保留旧数据”的要求；完成后归档；几小时后用户要求继续同一项调查，灵唤醒原 Agent 继续。

| 时点 | 真实对象 | 状态与动作 | 连续性证据 |
|---|---|---|---|
| 创建 | branch B、conversation C、episode E1 | 建立目标、fork 背景、来源/权限快照，状态 active；主干仍可聊天 | B.id 与 C.id 稳定；E1 的 predecessor 为空 |
| 独立执行 | E1/run R1 | coordinator 在 C 启动原生多步运行；工具 effect 与 checkpoint 完整保存 | 工作不影响主干；R1 归属 E1 |
| 中途指导 | guidance G | 进入持久队列，下一步真实消费后标 consumed；E1 的任务状态追加“旧数据保留”决策 | 能看到 G 被消费而非仅提交 |
| 最终完成 | E1/run R1 终态、task state T1、archive A1 | 核验 run/effect/交付后关闭 E1；向主干幂等回归；branch 转 dormant | T1 digest、A1 原文/hash、run 来源保留 |
| 等待与重启 | B、C、E1、T1、A1 | 应用重启仍能列出原 branch、旧 episode 和经历；不自动重放已完成 run | 旧归档字节与 hash 未变 |
| 再唤醒 | branch B、episode E2、run R2 | 检查旧 episode 已安全关闭后创建 E2，predecessor=E1；从 T1 和受控原文构造 R2；新 run 继续同一工作 | B/C 未换；E2→R2；R2 能读出目标、关键决策、未完成和证据 |

若 C 的关键历史被用户删除、换支或授权撤销，系统不能把摘要当成原文继续，也不能宣称 E2 完整恢复；应显示原因、保留 A1 只读，并允许用户创建新的受控请求。若只是应用重启且原 run checkpoint 仍有效，优先恢复 R1，而不是创建 E2。

## 五、修订后的实施顺序

| 包 | 重点 | 与旧计划差别 |
|---|---|---|
| P0 | branch/task-state/episode/run/archive 契约与迁移设计 | 不再等待全网络探针 |
| P1 | 创建、指导真实消费、安全结束、dormant、同 branch 新 episode/run、分阶段归档 | 子 Agent 本体首包 |
| P2 | 持久暂停、同 run recover、unknown/effect/lease、重启故障 | 连续性与执行安全 |
| P3 | 统一操作权限、L1～L4、审批生命周期 | 不阻塞主体闭环 |
| P4 | 网络隔离与 N0/N1/N2 实测 | 本体之后真实安全工程 |
| P5 | 管理 UI、episode/run 状态、经历入口、竞争刷新 | UI 服务端能力驱动 |
| P6 | 迁移、协议、性能、真实模型和 owner 最终验收 | 不能用旧 M2 结果替代 |

## 六、验收重点与未验项

S5 必须证明：同 branch ID、同工作 conversation、同 task state 前后版本、episode predecessor、旧归档字节/hash、后继 run 能读出原决策和未完成项；不能只断言“新 run 创建成功”。

S7 必须证明一次从需求、委托、指导、执行、归档到回归的完整任务在经历链中可追溯。S4/S6 必须覆盖暂停、重启、unknown、effect 和来源撤回。S8-S10 必须由真实通道验证权限交集；S9 还需负向网络探针。S14 的真实 provider 与所有者体验需要在授权范围内单独验证，费用/usage 未知如实保留。

本轮未验证新任务状态、episode、唤醒路径或权限实现；这些尚未存在。旧 N12/N16/N17 仍是未关闭项，真实 provider/owner 体验也未被新计划抹平。
