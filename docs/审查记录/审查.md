## 四、聊天、任务与旧模块专项调查

### 4.1 数据流与保存范围

普通聊天路径为 `session.ts::submit/connect` → `POST /chat/stream` → `ChatRuntime.submit` → 分支消息/附件 → `build_payload` → 原生多步循环 → 持久事件/SSE；断开 SSE 不取消后台 run。聊天用户文本在 submit 落库，助手最终文本仅正常完成且非空时落库；步骤中的可见输出另在事件流。界面 `refreshHistory` 读取消息和分支，当前没有事件折叠层。[前端会话逻辑](../../frontend/src/features/chat/session.ts)、[聊天 API](../../src/lingnexus/api/chat.py)、[对话服务](../../src/lingnexus/conversations/service.py)。

| 记录 | 当前权威位置/限制 | 阶段一用途与缺口 |
|---|---|---|
| 用户与最终助手文本 | `conversation_messages.text`；head/parent 构成选中分支 | 直接引用，不转存旧 history；删轮会物理删消息并断开部分 run 引用 |
| 工具调用/结果 | `chat_events.tool_started` 有参数，`tool_result.preview` 最多 800 字符；私有 effects/checkpoint 有较完整语义/原生材料 | 预览不能充当完整原文；需安全的持久语义来源与分页，不能直接开放 checkpoint |
| 中途指导 | 当前只进入 run payload/检查点，不进会话文本或独立 guide 事件（临时探针已证实） | P1 补指导来源和顺序，否则“完整经历”漏掉所有者指令 |
| 附件 | `conversation_attachments` 固定 hash/顺序；blob 原文校验；文本提取最多 12000 字节/128 段，原生内容受 8 MiB 限制 | 分别显示原文件与已提取片段，不能把提取片段当全附件 |
| 命令输出 | `execution_sessions` 与 artifact，输出采集有界 | 区分工具观察范围与存储缺失；按既有 run/owner/kind 授权读取 |
| 任务日志 | `task_events`/`task_steps` 可存完整工具 result，数据库写入路径未另设结果大小上限；底层工具仍有自己的上限 | 可作为来源但先做授权/敏感投影；不能一次全量装入模型或 UI |

当前未发现聊天事件、任务事件与命令记录的通用保留期裁剪；附件和 task-data 也不能据此保证永久保留。备份文件轮换是另一回事。新事件需要明确引用资产、覆盖范围、用户删除/撤回和未来清理契约，而不是增加一份无界正文副本。

### 4.2 独立任务并不会自动回到聊天

`tasks` schema、`Submission`、HTTP `TaskInput` 均无 conversation/message 字段；`tasks.protocol.initial` 只从 objective 和环境建立新 payload，不读聊天历史。任务页在聊天弹窗内显示，只是 UI 布局；`Snapshots.apply` 写工作区文件，不向会话追加结果。因此不能把同 agent/相近时间的 task 自动归入聊天事件。[任务入口](../../src/lingnexus/tasks/service.py)、[任务协议](../../src/lingnexus/tasks/protocol.py)、[任务 API](../../src/lingnexus/api/tasks.py)、[任务写回](../../src/lingnexus/tasks/workspace.py)。

任务 completed/needs_review/cancelled 与聊天终态集合不同；成果写回还可 conflict/unknown/部分完成。新事件要分别记录执行、验证、交付与剩余审阅，不能只翻译一个 status。可移植导出遗漏私有聊天 checkpoint/effects/命令会话，而完整 DB 备份保留；任务资产校验另有最多 4096 个任务、单文件 256 MiB、总量 2 GiB 等上限。[资产契约](../../src/lingnexus/maintenance/assets.py)。

### 4.3 旧服务可借鉴，不能直接恢复

`test_boundary_part1.py` 本轮专项运行 **4 passed**，临时 Application 也确认无 history/memory/identity 装配。可借鉴来源版本再校验、owner 修订审计、dedupe 作业和公开验证字段投影；不直接导入旧服务。

- 026 迁移后消息已无 `source_id`。临时探针调用旧 `Segments.source_event`，实际报 `no such column: source_id`；“旧分段只需装配即可用”的建议不采纳。[旧分段](../../src/lingnexus/conversations/segments.py)、[026 迁移](../../src/lingnexus/storage/migrations/026_conversation_message_text.sql)。
- `context/recall.py` 依赖当前不存在的 app.memory/app.history；旧 maintenance 的运行中保护依赖当前 manifest 已不产出的 recall_sources。需重新适配契约。[旧召回](../../src/lingnexus/context/recall.py)、[旧维护](../../src/lingnexus/memory/maintenance.py)。
- `tasks/store.py` 与 `maintenance/assets.py` 的同名 TASK_TABLES 清单用途和成员不同；新增表时核对运行器、导出与恢复的各自责任，不能只修改一处就宣称支持迁移。

开源子代理曾建议以旧 sources/source_revisions 继续作为新聊天权威；主 Agent 依据当前迁移及装配事实否决该建议。复用的是版本/来源模式，当前消息权威仍在 conversation_messages。

### 4.4 新发现的既有删除/恢复缺口（本轮未修复）

聊天专项临时 MockTransport 探针先建立带 checkpoint 的失败 run，再通过现有删轮接口删除该轮。结果：会话消息已删、head 与 run.user_message_id 置空，但 run 仍报告 recoverable=true；recover 被接受，模型请求数从 **1 增至 2**，新增请求仍带被删的测试提示词。持久事件与私有 checkpoint 也仍保留旧文本。

源码支持该路径：`get_run/recover` 未要求原用户锚点仍存在；`validate_head` 在两指针为空时可能通过。**“成功恢复后生成孤儿助手回复”仅为推断**，专项完整成功场景未走通，不能标为实测。[恢复路径](../../src/lingnexus/runtime/service.py)、[head 校验](../../src/lingnexus/runtime/failover.py)、[删轮实现](../../src/lingnexus/conversations/service.py)。

该发现不倒改 M1 历史验收，本轮也不越权修产品代码；已列为阶段一 P0 前置修复与 A7 新回归。事件失效不能仅处理摘要，还须阻断已删锚点的恢复/重发，并保留独立副作用围栏。另一个触发时序结论：BEFORE_TURN_END 在完成事务之前，不能在那里提前激活成功折叠。

### 5.1 优先参照：DeepAgents 与 LangChain

- DeepAgents 包版本 **0.7.26**，提交 `fd3e64ab6b605450bed5a2c22ef2ec84cd40542e`，MIT。直接依赖包含 LangChain、langchain-core、Anthropic/Google 模型包、LangSmith 等；本项目当前自有 httpx gateway 没有这套依赖。依赖接入可做适配，但不是可直接插入的薄模块，阶段一不采用。[包元数据](https://github.com/langchain-ai/deepagents/blob/fd3e64ab6b605450bed5a2c22ef2ec84cd40542e/libs/deepagents/pyproject.toml)、[许可](https://github.com/langchain-ai/deepagents/blob/fd3e64ab6b605450bed5a2c22ef2ec84cd40542e/libs/deepagents/LICENSE)。
- 其私有摘要事件保留原 messages，通过 cutoff 和摘要构建有效输入；会把淘汰历史追加到会话文件，并给出回查指针。**外存失败仍可继续压缩**，与本项目“来源保留成功后才能激活折叠”的要求不同。本项目借鉴可重建视图，不照搬该降级策略。[摘要中间件源码](https://github.com/langchain-ai/deepagents/blob/fd3e64ab6b605450bed5a2c22ef2ec84cd40542e/libs/deepagents/deepagents/middleware/summarization.py)。
- 上游 LangChain **1.4.6**，提交 `f37ca688f9e68f92c1f9161a342a8e709ac6b16e`，MIT；工具配对切点 `_find_safe_cutoff_point` 在上游，DeepAgents 通过 helper 复用。可借鉴“切点不能拆开调用与结果”的规则，但需要以本项目三协议原生对象重新实现。[上游中间件](https://github.com/langchain-ai/langchain/blob/f37ca688f9e68f92c1f9161a342a8e709ac6b16e/libs/langchain_v1/langchain/agents/middleware/summarization.py)。
- 外存使用 XML/文本渲染，不是原生对象的无损序列化：渲染器会忽略部分未知/内联内容，并截短部分块；媒体保存也依赖后端成功。因此“保存到文件”不能直接作为本项目逐段原文保真的证据。[渲染器](https://github.com/langchain-ai/langchain/blob/f37ca688f9e68f92c1f9161a342a8e709ac6b16e/libs/core/langchain_core/messages/utils.py)。
- 大工具输出旁路外存、旧工具参数裁剪和有限溢出重试有参考价值，**主要归阶段二继续研究**。阶段一不裁剪运行中的原生工具参数，不引入失败后盲目重试执行的路径。[大结果机制](https://github.com/langchain-ai/deepagents/blob/fd3e64ab6b605450bed5a2c22ef2ec84cd40542e/libs/deepagents/deepagents/middleware/_message_eviction.py)、[溢出裁剪](https://github.com/langchain-ai/deepagents/blob/fd3e64ab6b605450bed5a2c22ef2ec84cd40542e/libs/deepagents/deepagents/middleware/_overflow_clip.py)。

适配验证采用现有 MockTransport 边界：固定三协议夹具，检查完整交换替换、来源 hash、不合格摘要/外存失败保持 raw、多轮版本与分支隔离。上游测试定义仅用于补充场景，不能报告为本机通过。

其他已测结果：

- 16 条合成“闲聊→工作→闲聊”夹具中，30 KiB 级原生工作尾部仍能保留先前话题；200 KiB 及以上时只选最后 6 条，之前闲聊及发起工作消息均被截掉。大尾部是人工植入 completed checkpoint 的构建器压力夹具，**不证明该大小的单 run 能在同一窗口内正常完成**。
- 一次真实 ChatRuntime/本地 read_file/MockTransport 流程完成后，会话中最终助手文本为 4 字节；由该真实 checkpoint 构建的后续候选为 19,897 字节、11 个原生条目，证实显示文本长度不能代表下一次工具回放成本。此处没有测折叠效果，也不使用“整个包/四字节答复”的比值声称收益。
- 文本附件夹具中，附件估算为 12,142，ContextBuilder 总量已含此数；最终 manifest 又加一次，报 26,449 而非该构建器的 14,307。**重复计数已确认，仅该上报值重复**；选择阶段只计一次，后续完整 JSON 预检不使用该 manifest 总量。P0 校准此统计，避免未来节省对照失真。
- 最新单条超预算时构建器仍保留，随后真实运行循环还有完整请求预检；现有回归覆盖 context_limit 安全失败。探针的具体中间候选字节阈值不用于推断最终发送边界。
