## 用途与维护规则

仅供对话上下文恢复，可随时覆盖整理，不是正式需求或实施计划。保留有效结论，区分已确认、建议和待定。用户的新说明优先；涉及长期目标时回读原文。

每次推进时同步更新导航图、当前位置和正文状态。每个新的需求小步先联网核实相关官方文档或项目资料；区分文档事实、助手建议和实际运行验证。技术事实由助手调查，只询问用户的使用目标和重要偏好。

用户是编程小白，解释应使用简单语言、比喻和图表。成熟通用能力按功能组讨论，避免追问每个参数和异常分支。优先引用或复用成熟适用方案，有实际缺口再探索自研；不能未经比较宣称唯一最优解。

用户要求提高效率：无需用户决定的部分由助手查证后采用合理、可调整的工作默认并继续推进；只在存在实质使用取舍时提问。助手采用的默认不得伪装为用户明确确认，不因默认授权新业务或额外付费操作。

## 运行与恢复管理：本阶段收敛结论

当前阶段需求已收敛，区分用户选择与助手可调整工作默认；技术实现尚未选择。

目标：明确灵何时运行、怎样暂停退出，以及中断后怎样继续。不是备份系统，也不决定人格、记忆或自主活动内容。

功能工作默认：

- 启动、后台运行与退出：明确交流界面与实际运行的关系，提供明确退出入口。
- 暂停与继续：能暂停新活动并恢复；已发生的外部行动不能因暂停而撤销。
- 中断后恢复：保存已完成内容及任务进度，重新启动后区分已完成、待继续和结果不明的工作；不能为了恢复就盲目重复外部行动。

恢复的是持久保存的资料与可恢复的进度，不保证从任意机器指令位置无损续跑。已授权且仍适用的低风险工作可按记录继续，结果不明的外部操作先核实，不能擅自重复。用户主动暂停或取消的工作不因重启自动复活；错过的周期活动不默认全部补跑，记录情况并根据相关业务的有效期处理。具体策略按成熟机制实现，遇到实质产品取舍再提问。

用户已确认：关闭交流窗口或页面后，继续后台运行已启用的活动；只有用户明确退出整个程序才停止。此选择以电脑仍开着且未休眠为前提，不等于停机期间仍能运行，不授权新增自主活动。

用户已确认：默认由用户手动启动，同时保留以后开启登录 Windows 自启的设置。助手之前推荐的默认自启方案未被采用。明确退出后不在本次登录中自行重新启动；当前不要求登录前运行、强制唤醒电脑或无限崩溃重启。

- 安全显示：凭据、密钥和敏感内容默认不出现在日志或通知中；发送给外部模型的资料范围与结果应能被追溯到，但不要求把所有原文默认展示在提醒里。

状态观察与问题诊断的当前收敛：平时安静显示简洁运行状态；仅在需要用户处理的故障、权限请求、未完成任务、模型切换或重要变化时通知；需要时查看本地脱敏日志和任务／调用追踪。默认不接入第三方托管观测平台，不把模型输出当作可靠内部思维记录，不把敏感原文无条件写入日志或发送给外部观测服务。具体日志结构、追踪库和通知渠道留到第三阶段。

## 会话与交流情境系统：本阶段收敛结论

本系统按已确认的版本影响、自动分段和情境范围收敛；技术实现及与长期记忆的协作留后续阶段。

本系统讨论“交流如何被组织和保存”，不讨论模型如何连接，也不决定长期记忆如何形成。它像一组独立的谈话本：每本有自己的主题和上下文，可以重新打开；修改后可以产生新版本，但不把旧版本悄悄改写成从未发生过。

联网依据（2026-10-08，已读取，未安装或运行）：

- [Hermes Messaging Gateway](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/)按聊天保存会话，支持新建、重置、恢复、搜索和会话级模型覆盖；说明会话持续到重置，不等于每条消息都是新会话。
- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)区分线程级短期状态和跨线程长期资料，并支持从历史检查点重放或分叉；分叉保留原执行历史。
- [LangGraph Time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)说明从历史状态分叉可以探索替代路径，旧执行仍然保留；重放会重新执行后续模型调用和 API 请求，结果可能不同。

功能工作建议：

- 新建、命名、打开、关闭和恢复一次交流；用户可以明确开始新的交流，旧交流仍可回看。
- 用户已确认边界规则：由系统根据主题和时间自动划分交流，不采用仅手动新建或每次打开入口自动重置。手动新建与调整作为助手建议的补充能力。
- 区分交流状态：进行中、暂停、已完成、失败、等待确认；不要把“窗口关闭”自动等同于交流结束。
- 支持交流级设置与模型覆盖，但不自动改变灵的全局人格、权限或长期记忆规则。
- 保存交流的消息、附件引用、模型使用和重要操作记录；具体哪些内容进入长期历史／记忆由后续系统决定。
- 修改消息或重新生成后，从新版本继续；旧版本保留为历史记录或分支依据，不自动进入当前上下文和记忆。
- 允许从历史交流中搜索或恢复；搜索到的旧内容默认是参考资料，不自动当作当前事实。

推荐方向：采用“会话 + 可恢复状态 + 历史版本／分支”的组织方式；不把所有交流强行拼成一条无限增长的对话，也不因用户打开多个窗口就自动产生多个灵。具体会话数据格式、分支界面和记忆读取规则留到第三阶段及长期连续系统讨论。

自动划分的助手工作默认：像日记章节一样组织连续交流，在合适的轮次间切分，避免打断当前回复或取消未完成任务；新段保留必要的相关前情，分段不清空灵的身份、长期资料或权限。允许用户纠正划分。具体时间间隔与主题识别方法第三阶段实测，不声称存在唯一最优阈值；纯历史整理或重命名不触发模型切换。

与已确认备用规则衔接：开始新的交流段时优先主模型；当前段不因主模型恢复中途自动换回。自动分段不能擅自扩大授权、重复实际行动，或把旧编辑版本重新纳入上下文。已由旧版本产生的摘要／记忆须在后续长期资料需求中处理来源失效，不能只靠隐藏原消息假设旧影响已经消失。

本步联网核实（2026-10-08，未实测）：[Hermes Messaging Gateway](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/)明确当前默认会话不因空闲或跨日重置，时间重置通过可选 session-reset-policy 插件提供；因此只能参考会话保存和时间策略机制，不能声称其已提供适合灵的主题自动分段最优方案。[SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)支持给不同角色、用户身份或单次聊天绑定背景资料，证明情境资料范围管理有成熟参考，不证明灵必须采用世界书。

用户已确认情境需求：主要自然交流，必要时进入或退出用户设定的场景／背景。工作默认：可保存、选用和退出背景，并能辨认当前是否处于场景中；不会因自动分段自动退出场景，也不会因新段自动换人格。情境资料标明来源和适用范围，不能把场景叙述当成已执行的现实行动或已经证实的现实事实。场景经历能否及怎样影响长期记忆或人格留“长期连续与发展”讨论，不预先一律排除或纳入。

## 内容输入与表达系统：本阶段收敛结论

本系统按既定输入范围、正文与附件呈现的工作默认，以及用户确认的结果交付方向收敛。

沿用已确认输入范围：文字、图片／截图和常见文档，音视频以后再讨论。支持内容理解不自动意味着有图像生成或文件编辑功能。

通用功能工作默认：

- 发送文字并附带图片或文件；能辨认附件与相应消息的关系，看到资料是否接收、处理或处理失败。
- 正文能清楚呈现段落、列表、表格和代码等常见内容；图片和文件通过附件呈现，不因此决定网页或桌面技术。
- 回答基于所提供资料时，尽可能给出可核对的来源或定位；不能编造页码，区分引用、推断及未读取内容。
- 附件可保存和关联交流；日常交流的资料不会仅因展示或移除而自动变为全局记忆或从所有历史永久删除。资料跨交流的可用性随后续记忆／资料需求确定。

用户已确认结果交付范围：以文字回复为主，也能交付可保存的文档或其他文件；图片生成以后再考虑。具体输出格式和生成技术尚未选定；不自动承诺支持所有办公文件格式。生成文件的呈现属于此系统，实际制作与修改由工具行动系统协作。

## 经历与长期历史系统：本阶段收敛结论

所属位置：第二阶段 → 长期连续与发展 → 经历与长期历史系统 → 第三层具体功能与使用规则。

联网依据（2026-10-08，已读取官方／项目资料，未安装或运行）：

- [Letta Stateful Agents](https://docs.letta.com/guides/agents/memory/)将用户消息、模型消息、推理、工具调用和记忆等状态持久化，并区分 Agent、消息、运行和步骤。
- [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)区分单次线程／任务的检查点与跨线程长期资料，说明持久状态用于继续对话、处理中断和恢复故障。
- [LangGraph Time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)支持从历史状态重放或分叉，原路径保留；后续模型调用和 API 请求重新执行时结果可能不同。
- [Event Sourcing（Martin Fowler）](https://martinfowler.com/eaaDev/EventSourcing.html)说明可以把状态变化保存为事件序列，并由事件重建过去状态；这是架构思想参考，不表示 LingNexus 必须完整采用 Event Sourcing。

功能工作建议：

- 记录可观察经历：用户消息、灵的可见回复、模型调用基本信息、工具请求、工具返回、外部事件、权限确认、任务状态变化、成功／失败结果以及版本修正。
- 保留来源和时间：每条经历能知道何时发生、来自哪里、由哪次交流／任务产生、是否为用户输入、模型结果、工具结果或系统事件。
- 原始经历与当前版本分开：用户修改消息或重新生成后，当前交流按新版本继续；旧版本保留为历史回看，但不自动进入当前上下文或长期记忆。
- 记录行动结果：灵提出行动、系统批准行动、工具实际执行和外部结果分别记录，不能只保存“灵说它做完了”。
- 支持查看、搜索、导出和后续重建：长期历史应能回看某段经历，并为未来迁移和重新理解保留依据。
- 与记忆分开：经历系统保存“发生过什么”；记忆系统以后决定“哪些内容值得整理、检索和影响未来”。完整历史不会每次全部发送给模型。
- 隐私与安全边界：记录必要的事实和结果，不把隐藏思维链当作可靠经历，也不把凭据、密钥或敏感资料无条件写入日志或发送给第三方。

推荐方向：把经历看成“档案室”，把当前状态看成“从档案整理出的目录”，把长期记忆看成“以后会主动拿来使用的资料”。档案可以追加、修订和建立分支；当前视图可以选择有效版本；未来如果需要删除或归档，由所有者控制并保留影响范围。

当前不把完整技术模式定为 Event Sourcing。成熟方案已经证明检查点、事件记录、消息／运行／步骤记录和历史分叉都可行；第三阶段再根据数据量、迁移要求和业务关系选择轻量事件记录、检查点与普通持久化的组合。

本系统记录可观察经历和状态变化，不要求保存模型隐藏的完整推理过程。模型输出可能错误，工具结果可能失败，自动摘要可能失真；因此来源、状态和结果必须分开。经历记录也不自动等于永久记忆，长期记忆、自我理解和人格变化留给后续系统讨论。

## 记忆与知识系统：本阶段收敛结论

所属位置：第二阶段 → 长期连续与发展 → 记忆与知识系统 → 第三层具体功能与使用规则。

联网依据（2026-10-08，已读取官方／项目资料，未安装或运行）：

- [Mem0 How it works](https://docs.mem0.ai/core-concepts/how-it-works)把消息与提取出的事实分开，采用提取／检索两阶段，并支持添加、搜索、更新、删除和范围标识。
- [Letta Memory & dreaming](https://docs.letta.com/letta-code/memory)使用有界、可编辑的长期记忆，支持后台整理和人工查看；记忆在新会话中重新注入上下文。
- [Hermes Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)采用有界的 Agent 笔记和用户资料，并允许添加、替换、删除；文档明确提醒模型声称保存不等于实际写入成功。

功能工作建议：

- 从经历中提取记忆候选，例如偏好、约定、事实、目标、关系、经验和重要决定；原始经历保留在历史系统。
- 在模型调用前按当前交流、问题和权限检索相关记忆，只提供必要内容，不把整座档案馆搬到模型面前。
- 记忆带来源、时间、适用范围和可信状态；区分用户明确确认、系统从经历推断、暂未确认和已过期内容。
- 支持更新、纠正、归档和删除；新信息不应静默覆盖旧事实，发生冲突时保留变化关系并以当前有效状态参与后续使用。
- 记忆按范围隔离：灵的长期资料、用户资料、某次交流资料、某个场景资料和外部知识不能默认混为一类。
- 记忆是否写入、修改和影响后续行为应可追踪；自动整理失败或模型判断不可靠时，不伪装成已完成记忆。

用户已确认记忆保存方向：只要系统判断某项内容值得记住，就自动保存；用户主要在发现问题时查看和纠正，不要求每条记忆提前确认。由此保留以下保护：自动保存不等于不可修改；每条记忆带来源、时间、范围和可信状态；支持纠正、回退、归档和删除；涉及敏感资料仍按所有者权限和资料访问边界处理。自动记忆判断失败时如实记录，不能声称已经保存。

记忆与知识系统当前收敛：支持自动提取、检索、更新、纠正、归档和删除；区分原始经历、用户资料、灵的长期资料、交流／场景资料和外部知识；检索结果按当前权限和交流需要提供给模型。具体检索、存储和评估技术留第三阶段。

## 第三阶段约束：上下文组织、注入与前缀缓存

用户已明确澄清：人设、记忆以及其他内容的注入，应该尽量避免破坏 LLM 前缀缓存命中；在此基础上，尽可能降低长上下文带来的注意力偏移。不是“不必在意缓存命中”。本项属于第三阶段实现原理探索，涉及模型接入、上下文组织、记忆检索、人格状态、会话分段和历史修订，不能当作单个 API 参数解决。

2026-10-08 联网核实，已读取资料，未调用模型实测：

- [Claude Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)说明按 tools、system、messages 的顺序匹配完整前缀；缓存点之前的修改会影响该前缀的匹配，仍可能复用已缓存的更短共同前缀。文档建议将稳定内容置前并在适当边界配置缓存；有效期、最低长度、模型及平台支持等均影响实际命中。
- [Lost in the Middle](https://arxiv.org/abs/2307.03172)在特定模型及多文档问答、键值检索任务上发现相关信息位置和上下文长度会影响表现；这是风险和测试设计依据，不证明所有当前模型必然有相同程度的问题。

已证实的区别：前缀缓存主要复用输入处理，降低延迟或成本，并不把长上下文变短，也不能单独解决注意力偏移。高缓存命中不等于能正确使用记忆，支持大上下文也不等于在所有位置都能可靠取用信息。

第三阶段研究候选（助手建议，尚未选型）：

- 区分长期稳定的规则与实际会变的人设／记忆内容；比较稳定前缀、可复用历史与按需注入内容的组合，不把所有记忆每轮重写到提示最前面。
- 比较按相关性选择资料、限制重复与无关内容、近期上下文和带来源摘要的组合；缓存后的历史仍须控制长度，不能只为命中率无限追加。
- 对更新、撤回、编辑分支和重大人格变化建立明确的上下文生效规则；必要时重建受影响部分，不为保持缓存而继续使用已失效资料。既定用户修正规则仍有效。
- 分别测量缓存读取／写入用量、输入长度、延迟、实际费用，以及关键约定召回、位置敏感性、修正生效和人格一致性。不预设统一长度阈值或声称某种排列全局最优。
- 按用户实际模型和 API 渠道核实缓存机制；第三方兼容 API 不自动等于缓存行为一致或提供同等统计。缺少统计时明确无法验证，不以延迟猜测命中。

本轮只记录约束和研究方向，不据此采用任何框架、冻结人设或推迟已确认记忆的必要生效。

## 第三阶段专题一：三端点、流式与思考展示

## 第三阶段专题二：外部事件与主动活动可行性

结论：无需从零发明机制。定时调度、文件监听、事件接收、持久记录及 Agent 运行均有成熟参考；灵需要设计的是何时值得触发、如何结合目标与记忆、怎样验证行动及控制打扰。用户进一步明确：灵需要主动对外界作出反应，不能只限于被动答复或预先设置的定时任务；既关注与所有者相关的事情，也能在允许范围内探索外部信息。

具体案例（2026-10-08 实际读取文档，未安装或测试）：

- [Hermes Cron](https://hermes-agent.nousresearch.com/docs/user-guide/features/cron)：一次性和周期任务、暂停修改、隔离 Agent 会话、脚本无模型模式和外部事件触发；不照搬全部默认行为。
- [Hermes Session Heartbeats](https://hermes-agent.nousresearch.com/docs/user-guide/features/heartbeat)：空闲时触发，同一会话续接，用户消息优先，错过多次合并，无有意义变化则静默；通过追加消息避免修改系统前缀。其“cache-safe”是前缀组织方式，不保证真实云端命中，仍取决于 TTL 等条件。
- [Hermes Webhooks](https://hermes-agent.nousresearch.com/docs/user-guide/messaging/webhooks)：外部通知经过认证、过滤、合并，再触发 Agent 或既有任务；回调能抵达本机需要明确网络路径。
- [Hermes Architecture](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)：网关、统一 Agent 循环、工具分发和会话存储协作，是可参考的产品实现。
- [APScheduler 3.x User Guide](https://apscheduler.readthedocs.io/en/3.x/userguide.html)：提供一次性／间隔／日历调度、持久 job store、错过合并和并发实例控制；3.x 与其他版本 API 不混用。只解决调度，不自动保存整个 Agent 执行进度或保证外部动作仅执行一次。
- [watchdog 官方仓库](https://github.com/gorakhargosh/watchdog)：支持 Windows、Linux 等文件事件监听。旧 stable 教程为较旧版本，实现时选定当前受维护版本后核实。

适合当前条件的组合建议：本机常驻后台 + 调度器候选 APScheduler + 文件监听候选 watchdog + 应用自有持久事件／活动／执行记录（SQLite 候选）+ 统一 Agent 执行器。外部网页或服务初期按授权采用轮询；有明确可达回调入口时再接 webhook，不为此默认启动 Linux 或公开本机端口。框架只在实现验证后选定。

处理链：时间／文件变化／工具完成／指定外部更新 → 登记事件 → 去重、合并与授权检查 → 判断是否需要模型 → 排队 → 既有 Agent 执行器 → 验证并记录结果 → 必要通知或静默。简单状态检查可用普通程序完成，不必每次花费模型调用。

三种主动性要区分：按时执行既有任务；定期检查未完成事项和变化；根据经历及目标主动提出下一步。前两种已有明确成熟机制，第三种可用模型和状态规则实现，但是否有用、稳定、符合灵的长期方向需要实验，不能用“装了定时器”宣称自然产生内在动机。

沿用用户预授权规则：低风险活动可在范围内自行创建，其他活动确认；创建的活动也有可查看的目的、来源、范围和暂停入口。避免活动反复生成活动、文件写入自触发、重复事件重复操作和暂停后复活。执行失败或结果不明按既定恢复规则处理。这里不重新加入用户已拒绝的费用预算停机。

会话策略：独立周期工作使用独立任务上下文；需要当前交流前情的周期检查使用关联会话。主题自动分段时保留显式任务关联，不因新对话丢失活动，也不把后台日志无限塞进主对话。人设稳定前缀尽量复用，动态事件在适当位置追加，周期清理无关上下文；本机睡眠／退出期间不执行，恢复后合并或跳过已失效检查，不伪称 24 小时持续运行。

原型验证场景（尚未执行）：定时提醒、指定文件变化、编程工具完成后继续、无变化不通知、忙时用户优先、重启后计划恢复、重复事件只产生一个有效任务、自触发受控、撤销后不再启动，以及思考／缓存兼容。

现成框架集成可与轻量组合路线并行比较。推荐先验证轻量模块组合；如选择 Hermes 执行框架，则优先复用其调度／事件能力并对齐灵的规则。当前不叠加多个调度平台，也不需要为了本机阶段引入 Temporal 或完整分布式消息系统。

### 主动观察与反应的扩展（本次补充）

用户已确认：需要同时关注所有者相关事项和允许的外部信息。这是未来产品需求，不是立即监控用户电脑、读取全部文件或自动访问网站的操作授权；现实信息必须来自已接入且有权限的数据来源，不能根据对话猜测用户当前活动并当作观察事实。

建议的闭环：维护关注事项 → 决定要观察什么及何时再看 → 从授权来源观察／查询 → 与先前情况比较 → 检索相关记忆和目标 → 判断变化是否有意义 → 选择暂不行动、继续了解、与所有者交流、准备资料或执行授权行动 → 核实结果并更新经历与关注事项。

关注事项可以来自用户明确关注、既有目标、未完成事务、过往约定，以及从经历中提出的兴趣或问题。关注事项不是强制执行的任务；观察没有新发现可以结束，也可以在已有授权范围内选择新的观察方向。重大长期方向变化仍需确认。

推荐将两层分开：普通程序负责可靠唤醒、收集变化、过滤重复、排队和保存结果；模型结合记忆、目标和当前情境判断关注重点与下一步。动态观察片段按需提供，避免每次重写整个人设或发送全部观察记录；保持前缀缓存友好但不让过期资料影响决策。非必要的重复检查可先用程序完成，真正需要理解时再调用模型。

“主动反应”可体现为四类：主动关注并回访、主动查证和探索、主动发起有依据的交流、主动完成已授权的低风险工作。具体交流频率与呈现方式为后续体验策略；不能把技术日志通知规则硬套为“只有故障时灵才可以说话”。也不默认要求每天问候或定期无意义汇报。原来“系统状态无变化不重复通知”的规则继续有效。

原型场景建议（未执行）：

- 用户曾讨论一个项目，授权的项目出现与目标相关的变化；灵自行发现、对照旧认识、准备有来源的建议，而不是等用户逐次要求检查。
- 用户允许关注某个主题；灵从已授权资料源发现新进展，主动查证并判断与用户和既有目标的关系，再选择是否分享。
- 初次发现的信息不足以作结论；灵在授权范围内自行查阅补充资料，明确区分发现、推测和确认结果。
- 无相关变化或只是重复内容时不制造工作；当前用户正在交流时遵守前台优先；权限撤销后停止相应观察。

评价应包括发现是否有依据、是否相关、误报和重复打扰、是否完成有用行动、纠正后是否调整，以及模型费用和缓存利用；不能仅以主动消息数量或任务数量证明主动性成功。具体观察范围和用户允许的来源后续配置，不能凭原则授权全机全网观察。

本步联网依据（2026-10-08，已读取，未安装或测试）：

- [Hermes Session Heartbeats](https://hermes-agent.nousresearch.com/docs/user-guide/features/heartbeat)：没有新用户消息时也可在空闲触发检查，支持用户优先、无变化静默和不修改系统提示的消息注入。它解决唤醒与续接，不直接决定灵的长期兴趣。
- [Hermes Persistent Goals](https://hermes-agent.nousresearch.com/docs/user-guide/features/goals)：目标跨轮保留，执行后判断继续、完成或受阻，说明不需要用户逐轮催促的持续执行已有参考；文档中的模型判断仍需实际结果验证。
- [Generative Agents](https://arxiv.org/abs/2304.03442)：模拟环境中，观察、记忆、反思与计划共同支持主动交流和行为。属于主动个体的研究案例，不能当成现实 Windows 个人 AI 的完整现成方案。

方案判断：基础调度、观察连接器、持久化及 Agent 工具执行优先复用；灵专属的关注管理、关联判断、行动选择与交流策略需要组合设计和实验。既不需要发明全新计算原理，也没有依据认定安装一个心跳或任务框架就自动实现长期愿景。

### Jev 决策模型辅助主动性（用户提出，已初步调研、待验证）

用户提出：接入 Jev 这类廉价决策模型，判断是否应该主动反应。当前结论是值得优先验证，但不是已确定采购或采用；尚未安装 SDK、配置凭据或调用付费 API。

2026-10-08 已读取的一手资料：

- [TypeSafe Introduction](https://docs.typesafe.ai/introduction)：Jev 是 System One 决策模型，输入 state 与 questions，输出 Choice（有限选项及概率）、Score（有序等级评分及概率）、Noul（是的概率）。不生成自由文本；多问题可同次请求，但各问题独立评估。
- [Models](https://docs.typesafe.ai/models)：当次页面列出 jev-1.13.0，按输入收费，每百万输入 token $0.042，输出免费；文本输入，含 JSON 文本状态；总请求 64k，state 加最长问题 32k。英文效果最好，中文等需实测。价格和模型版本以后重新核对。
- [Quick start](https://docs.typesafe.ai/introduction/quickstart)：原生 POST https://api.typesafe.ai/v1/systemone，需自己的凭据；不是此前三个主模型 API 的同名模型直接替换。
- [Confidence](https://docs.typesafe.ai/confidence)：Choice／Score 的 confidence 由输出概率分布计算；Noul 只给 yes 概率，没有独立 confidence。不能把 confidence=0.9 解释为在灵的任务上必有90%正确率。
- [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)：官方公开算术、计数、时间比较、复杂间接推理、无关长上下文、诱导文本、选项顺序及文本生成等局限。首页营销中的零幻觉不能解释为零误判。
- [Skill suggestion cookbook](https://docs.typesafe.ai/cookbooks/skill_suggestion)：厂商使用固定 Hermes 技能目录、Jev 1.12 和特定主模型进行两阶段技能推荐，保留主 Agent 自己判断；488条测试中含生成式合成请求。可参考分级筛选和稳定前缀外追加建议，不能把数字直接迁移为灵的主动判断效果。

其他集成参考：[Pydantic AI TypeSafe](https://ai.pydantic.dev/models/typesafe/)已有模型适配和升级到生成模型的模式；[LiteLLM Decisions](https://docs.litellm.ai/docs/decisions)提供 System One 决策接口适配，注明不流式。存在适配不代表必须为此引入框架。

推荐分工：

1. 普通程序处理权限、去重、时间计算、冷却、来源选择和已知事件规则；明确的用户任务、已承诺的提醒及必要故障提示不交由概率分类器决定是否丢弃。
2. 准备小份事实资料：新观察、有关关注事项、相关记忆、已处理过的变化及当前交流是否忙碌。身份完整历史、无关网页和代码不全量传给 Jev。
3. Jev 分别判断“是否相关”“相对旧信息是否有实质新增”“是否涉及需及时留意的变化”“资料是否不足”“最接近哪个已有关注事项”；不要只问一个包揽价值、权限和行动的巨大问题。日期是否到期、计数等由代码完成。
4. 程序根据经测试校准的规则，选择忽略／归档、延后、交主模型判断；不确定和可能重要的情况升级，而不是默认忽略。周期抽查被过滤样本，检测漏判；保留主模型定期整体回顾与探索机会，避免只能注意既有目录内的事。
5. 主模型负责形成新的关注方向、深入查证、决定具体交流内容与计划；实际执行仍过权限规则，Jev 高置信度不能授予权限或免除重大操作确认。
6. 根据实际结果和用户反馈更新关注资料及测试样本；不是默认在线训练 Jev。模型版本、问题版本和判断结果可追溯，阈值适用于经过测试的版本。

这是一项辅助判断用途，不替换用户选定的主模型或备用模型。主模型处理需要生成或多步推理的工作，辅助模型负责有限判断。若采用 Jev，新增独立的决策服务适配及配置；三种既定主模型端点仍照常支持。decision API 不要求流式或思考面板，不能编造其未返回的理由文本。

费用示例：假设含 state 和全部 questions 的计费输入为每次2000 token，每天10000次判断，按当前直连标价为2000×10000÷1000000×$0.042=$0.84/天，仅用于说明量级，不是计划频率。需另计观察获取、文本提取／图片转文字、摘要、主模型升级、重试及第三方加价。没有变化不必按秒反复调用；费用控制仍沿用只统计、不自动预算停机的用户选择。

对缓存的影响：Jev 调用与主模型上下文分开；传给主模型的是必要事件、来源与少量决策辅助信息，不把全部筛选日志反复插入系统提示前部。不同模型之间不能共享前缀缓存；本轮未查到足以承诺 Jev 前缀缓存行为的官方说明。不要为缓存保留失效记忆。

验证计划建议：比较规则筛选、普通低价 LLM、Jev 加主模型，以及直接主模型的结果，使用中文真实近似场景与留出的测试样本。测试漏掉重要变化、误唤醒、语境不足、选项顺序、诱导内容、模型版本变化、延迟和总链路费用；主模型判断不是绝对真值，以任务事实和用户偏好核验。不预设0.8等万能阈值。新模型初期可只记录建议、与实际判断对照，验证后再控制唤醒。

关键结论：Jev 能帮助低成本地“挑出值得进一步注意的事”，但持续维护关注事项还需要持久状态、定期回顾和主模型生成新的理解。分类器漏判会限制灵的视野，因此不能成为所有主动性的唯一入口。

### 推荐整体结构：持久经历与状态 + 有限的工作上下文

比喻：工作上下文是一张书桌，少量身份与当前状态是桌上的卡片，事件概览是目录，详细经历是档案，技能是操作手册。保存到档案不意味着模型本轮看到了；从桌上撤下也不等于删除档案。

| 第二层系统 | 持久保存的主要内容 | 对当下交流和行为的作用 |
|---|---|---|
| 经历与长期历史 | 用户消息、灵的表达、授权观察、工具调用与真实结果、附件引用、版本和来源 | 提供可核对的原始经历；区分说过、推测、尝试过与已成功 |
| 记忆与知识 | 事件卡、主题／时间目录、事实与认识、出处、适用范围及失效状态 | 主动提供少量相关记忆，允许模型继续查阅细节 |
| 自我理解与人格 | 当前有效的身份与倾向、小量行为例子、形成依据、版本与候选变化 | 编译成有界的核心说明和本次相关补充 |
| 反思与学习 | 复盘、经验候选、验证结果、知识修订、技能／流程及失败教训 | 将经历变成未来可复用的行为改进；写了反思不等于已学会 |
| 长期状态与发展 | 目标、关注事项、承诺、能力证据、当前进度及变更历史 | 影响检索、计划和主动活动；不能只存在于可能被摘要丢失的聊天里 |

共同基础只提供存储、标识、版本、权限及变更通知等通用能力；五系统通过明确接口协作，不把全部业务塞进中心。上下文组装跨系统挑选本轮资料，不成为新的全能业务中心。

### 人格如何获得持续影响

- 云端 API 没有通用的“人格注意力权重”旋钮；system／developer 指令是优先级机制，不是保证注意力或逐条遵守的硬权重。XML、Markdown、重复“绝对遵守”均无绝对保证。OpenAI 和 Anthropic 按实际接口映射其支持的指令入口，不假设三端点内部效果相同。
- 推荐把简短、无冲突、当前生效的核心人格和稳定行为原则放在应用指令层；描述可观察行为，必要时用少量典型例子。初始设定不是永不变化的最终人格，保持版本和用户纠正入口。
- 详细自传、人格形成经历、特定情境的偏好按需取用。外部资料、历史原话、模型推断、虚构场景不能直接提升为核心人格指令。主观自我解释与客观事件分开记录。
- 每次压缩／重建上下文都从已保存的当前有效状态重新装入核心，不依赖摘要模型恰好保留它。关键权限与确认要求由程序执行，不依赖人格提示遵守。
- 稳定核心在一段连续调用期间保持前缀一致；新经历在后部追加。确认的人格变化和用户纠正必须及时生效，必要时使受影响缓存失效，不能为命中而保留错误。可比较针对当前任务的短提醒，但不默认每轮复制整个人格或声称放在末尾一定最好。
- 验证长对话、压缩、切换主／备用模型、工具任务、场景进出后的一致性和修改生效；有界上下文及模型能力同样决定结果。

### 事件记忆：概览→事件卡→原始细节

用户的“主题与时间分段”可作为事件形成线索，但会话片段不等于事件：一个长期项目可以跨多次交流，一个片段也可能涉及多件事。事件有稳定 ID，可关联多个片段和文件；主题标签允许多个，不强制每件事只有一个父类别。纠正分段不应破坏已有引用。

主题／时间目录（大目录也分层，不能全量常驻）
                        ↓
事件卡：时间、参与者、起因、经过、结果、关键决定及原因、
        对灵／用户的意义、尚未解决的事、别名和原始证据引用
                        ↓
原始消息与版本、工具结果、附件及可定位的具体片段
~~~

- 事件进行中维护暂存状态，阶段完成／暂停／上下文接近阈值时形成摘要，不等无限期“彻底结束”。不要每条消息都重新总结全部历史。
- 最近和正在相关的事件摘要进入工作上下文，旧事件进入长期目录，仅保留必要概览。全部事件各压成一句仍会无限增长，需要分层与选择；不要无限“摘要再摘要”且抛弃来源。
- 摘要有损，原始记录需保留才能核实被省略的细节。金额、日期、原话、关键约定等需要精确时取原文，不能让模型从概览补造。可以验证原文可读取和引用完整，不能保证模型每次都选对、理解对或自然想到每件事。
- 摘要记录因果、意义和未完成事项，不只列事实关键词；“灵觉得这件事重要”仍标记为解释，不冒充用户确认的事实。
- 用户编辑消息／选定新回复后，标记受影响摘要、认识、人格候选及技能依据失效或待重算；旧分支只供回看，不进入默认召回。原始记录不会被后台摘要覆盖，仍遵守明确的数据删除／维护操作。

### 不依赖向量库和图谱的召回路线

推荐组合：显式事件／任务关联 → 时间、主题、人物、文件等条件缩小范围 → 关键词／全文查找（含别名）→ 模型阅读有限目录和事件卡 → 需要时取原始片段。先用程序完成低成本的确定性定位，语境模糊时让模型逐步查询。目录导航和全文搜索互为补充，避免归错一类就永远找不到。中文分词、短词、简称和模糊指代需要专项验证，不能认为接上 FTS 就已经解决中文召回。

两种回忆入口：程序根据当前活动、时间或显式事件自动提供少量线索；模型遇到“那次”“后来怎样”等指代或证据不足时主动查档。提供探索／回顾机会帮助联想，避免所有回忆都必须用户主动提问；联动已讨论的关注事项与主动活动系统。Jev 可辅助分类和候选排序，但不能生成事件摘要，也不能成为阻止重要回忆的唯一门槛。

方案比较：全历史／全部摘要常驻只适合小规模基线，会随历史增长；纯目录导航适合概览到细节，但模型检索轮次及误导航有成本；目录、元数据、全文查找、主动查阅的组合是当前推荐验证对象，尚无证据为本项目全局最优。这里仍有广义的“取资料再回答”，但无需使用向量数据库或知识图谱。

### 学习成果存在哪里、怎样生效

当前主要采用外部持久资料和工具带来的系统学习，通常不修改云端模型权重。仅保存文字不构成有效学习：必须在相似但未见过的新任务上能正确调用，并得到结果支持。

| 学习成果 | 建议保存位置／形式（逻辑归属，不是最终文件布局） | 生效路径 |
|---|---|---|
| 新事实／领域知识 | 知识条目及来源材料，记录时间、范围、证据和不确定性 | 相关时查阅、过期时核验 |
| 一次经历和教训 | 事件卡、复盘、失败原因、反例 | 相似情境触发参考；不把一次失败无限泛化 |
| 可复用做法 | 技能目录：说明、适用条件、步骤、脚本／模板、验收办法及来源事件 | 按需加载、授权执行、验证结果 |
| 自我认识／人格变化 | 有版本的当前状态与候选记录 | 按既定确认规则生效后更新人格输入 |
| 新目标／关注事项 | 结构化目标和关注状态 | 进入规划／主动活动，沿用权限规则 |

流程：经历与真实反馈 → 形成带来源候选 → 检查冲突及适用范围 → 按风险分级生效／待用户确认 → 在新情境中使用并验证 → 保留、修订或回退。普通经验与低风险行为调整自动形成；涉及身份、关系、价值判断、重大人格或重要能力变化的反思先存候选，用户确认后生效。不能通过写入技能／记忆绕过确认。

Skill 适合程序性知识，不能独自承担完整自传、事实库、当前身份和目标。事实可立即作为“有来源但待进一步核实”保存，不要求每条知识都跑程序测试；编程技能应保留实际测试结果，不能凭模型自评宣称掌握。长期反思应有新证据和停止条件，不让相同材料不断反思而把猜测强化成事实。

存储候选：本地 SQLite 保存记录、状态、来源和版本；Markdown／JSON 用于可读条目、技能和导出；大文件／附件放文件存储并由稳定 ID 引用。需要指定每类资料唯一的权威来源及编辑回写规则，不能同时让数据库和散落文件独立为真。这是轻量实现候选，不是最终选型或必须采用 Letta 的 Git 存储。重要长期资料可迁移；提供方加密压缩状态仅作运行续接，不能替代自有经历档案。

### 上下文与成本

- 工作上下文按实际模型预算：核心指令／人格 + 当前目标／状态 + 近期对话 + 所需记忆／知识／技能 + 工具输出。另预留输出／推理及下一次工具结果空间；工具描述、图片文档和不透明状态也可能占额度。不能把全部窗口都分配给历史，更不能统一套一个比例或 token 数。
- 采用连续调用内稳定前缀与追加历史，在事件边界或预算阈值处换成经过核对的短工作状态；重要身份／约定／未完成任务单独保留。不要每轮重写早期消息破坏缓存，也不要为了缓存无限保留旧历史。
- 缓存命中降低重复输入的部分费用和延迟，不减少模型需要处理的语义内容，也不等于免费。长期落盘容量与每轮发送 token 分开控制。
- 简单规则、时间与全文查找先用本地程序；摘要只处理新增／变更事件；有意义的复盘集中后台处理；复杂查证或技能学习再投入强模型。小模型需要与遗漏风险一起评估，不能让廉价错误导致高额返工。
- 总费用包含前台回复、摘要、目录维护、回忆多轮、反思、验证、主动活动、重试等全部调用；只比较主对话输入价会误导。按用户既定选择展示用量与费用，不擅自新增预算提醒／自动暂停。

### 已读取依据与适用边界

1. [Letta MemFS](https://docs.letta.com/concepts/memfs/index.md)：根目录少量记忆每轮进入系统提示；带目录的深入资料按需加载；默认无向量／语义索引；普通文件工具查找，Git 保留版本。最贴近本轮需求的现成机制参考，不等于长年可靠回忆已获证明。
2. [Letta Memory & dreaming](https://docs.letta.com/configuration/memory/index.md)：后台回顾、整理、检查记忆；文档中的 Agent reviews before applying 是代理复核，不是用户审批，不能直接替代灵的重大变化确认规则。
3. [Anthropic Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)：轻量标识、按需取资料、逐步展开、压缩、结构化笔记、子代理隔离；明确过度压缩会丢失关键细节。
4. [PageIndex 官方项目](https://github.com/VectifyAI/PageIndex)：用目录树和 LLM 推理检索长文档，无需向量库；主要面向文档，不是动态自传记忆成品。项目的相似度对比和基准结果不能当作所有向量方案都无用或灵已验证的证据。
5. [Hermes Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)、[Skills](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)：有界常驻记忆、按需程序性知识、从任务经验创建技能；当前记忆为会话开始快照，不能不加修改地照搬来延迟灵的重要纠正。
6. [LangMem Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)：事实／经历／程序性记忆及前台／后台写入的区分，提供职责参考，不因此选定框架。
7. [MemGPT](https://arxiv.org/abs/2310.08560)：分层记忆和有限上下文的早期研究；[Reflexion](https://arxiv.org/abs/2303.11366)：文字反馈改进行为，不更新权重；[Voyager](https://arxiv.org/abs/2305.16291)：可执行技能及环境反馈，研究环境是 Minecraft；仅借鉴这些机制，不采纳它们全部检索方案。
8. [LongMemEval](https://arxiv.org/abs/2410.10813)：信息提取、跨会话与时间推理、知识更新、无依据时不作答，用于设计评测；[Lost in the Middle](https://arxiv.org/abs/2307.03172)：特定早期模型／任务的位置敏感性证据，不泛化为现代模型固定衰减阈值。
9. [OpenAI Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)、[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Compaction](https://developers.openai.com/api/docs/guides/compaction)：指令、缓存、续接机制；Responses 压缩项不透明，不能成为跨提供方唯一长期记忆。
10. [Anthropic Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[SQLite FTS5](https://www.sqlite.org/fts5.html)：缓存与可选全文检索实现依据，具体模型／渠道和中文效果仍需验证。

### 下一步验证与尚未解决的问题

先以目录／事件卡／原文和有界人格构成最小验证方案，与“近期上下文＋单份滚动摘要”的简单基线比较；当前不直接引入完整记忆平台。需要实际模型和渠道后才能测费用与可靠性。

应覆盖：多次主题切换后的人格行为、压缩后身份和目标、模糊指代的旧事件、摘要遗漏的精确原话、同主题不同时间的事件、跨主题关联、用户修正／旧分支失效、虚构场景和现实区分、不存在的经历能否承认未知、学到的方法在新任务上是否有效、重启及切模型后连续性。分别计量定位成功率、证据正确率、读取后答对率、误回忆、延迟和总成本，而非只统计“调用了记忆工具”。

待细化：核心人格如何由现有设定提炼；事件卡最小字段及主题边界；自动提供什么线索、何时模型主动查档；失效传播和重建规则；各类学习的验证；各模型上下文软预算。当前证据支持工程可行性，尚不能承诺像人类一样的体验或永久无损回忆。

### 对照 01／02 后的演化补强与编码收敛（2026-10-08）

用户再次强调：角色扮演只是可能的表现形式，人格必须能演化；要求继续探究直到可正式编码。已经重新完整读取 01 与 02；此前方案包含演化，但仅描述可编辑状态不够，需要明确“经历→候选→生效→影响行为→真实结果”的闭环。

- “核心人格常驻”统一理解为当前有效的短自我状态，不是冻结初始人设。所有者边界、自我状态、暂时情境和历史解释分别保存。
- 初始人设仅初始化一次；退出场景、压缩、重启和切模型读取最新有效状态。人格评测同时检验无依据偏移和获批变化能否真实影响行为，不要求永久与初始角色一致。
- 变化候选采用来源＋base_revision＋总体影响判定；受保护的身份／关系／价值等仍待确认，小改动累积成重大变化也须升级，不能通过分拆技能或记忆绕过。
- 更正经历只使关联派生认识待重评，独立的后续成长不一并抹掉。新的解释与原始经历分开，不能把状态回退当作现实行动被撤销。
- 当前没有阻塞第一批开发的用户偏好缺口。后续联调才需要实际主／备用服务、凭据的本机配置、目录与外部来源授权；初始人格可后来补充，不擅自编造。

| [Mem0](https://docs.mem0.ai/core-concepts/how-it-works)、[OSS](https://docs.mem0.ai/open-source/overview) | 记忆提取、查询、修正 | 不替代完整经历；托管与开源能力不同 |
| [Generative Agents](https://arxiv.org/abs/2304.03442) | 观察、记忆、反思与计划关系 | 受控模拟研究，不证明现实长期发展已解决 |
| [Temporal](https://docs.temporal.io/encyclopedia/durable-execution) | 长任务与故障恢复 | 当前可能过重；任务恢复不保证外部动作自动恰好执行一次 |
