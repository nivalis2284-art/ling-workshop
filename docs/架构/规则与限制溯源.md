# 规则与限制溯源审计

> 创建日期：2026-10-11
> 状态：滚动更新（每发现一条"来历不明的限制"就追加一条）
> 目的：把项目里那些「你不知道为什么存在」的规则，逐条追到需求原文，判断它到底是
> **需求要的** / **实现自加的** / **方案被固化的**。

---

## 审计方法

每条限制按五栏记录：

1. **限制是什么**（今天项目里的实际行为）
2. **需求出处**（哪份文档、哪一行）
3. **需求实际说了什么**（原文，不做转述）
4. **实现做了什么**（实际代码行为）
5. **判断**（需求要的 / 实现自加 / 方案固化）+ 建议

判断标准：

- **需求要的** → 保留。
- **实现自加** → 需求没要求，是实现者为了"更安全"自己加的。**默认候选删除项。**
- **方案固化** → 需求只提了约束，实现挑了个手段，然后手段的细节变成了项目的一部分。**需要重新比较手段。**

## 审计 #2：Docker 执行沙箱

### 2.1 先分清两条完全不同的线

| | 你说的「Docker 部署」 | 项目里的 Docker |

| 指什么 | 把 LingNexus 本身部署到 Docker 上运行 | 用 Docker 容器当**编程任务的执行沙箱** |
| 文档里记成了 | 「Linux 部署 / Linux 迁移」 | 「隔离编程」 |
| 状态 | **未实现**，明确列为未来扩展 | **已实现**，且是编程任务的前置条件 |

**「Docker 部署」的出处**（三处，全部指向"以后再说"）：

- `../归档/首版与第一部分改造/研究/2026-10-08-阶段讨论记录.md` 第 242 行：「用户有高性能本地硬件及轻量 Linux 服务器，但**本地模型与 Linux 部署仅作未来扩展**」
- 同上第 383 行：「**Linux 服务器仍是未来扩展**，不能自动纳入当前备份」
- `../归档/首版与第一部分改造/计划/2026-10-08-完整Windows首版.md`「交付边界」：「**Linux 服务端**、本地模型、多设备、音视频、图片生成**不是本次范围**」

→ **"部署到 Docker"这件事，项目里一行都没做，只是被记成了"未来扩展"。**

### 2.2 项目里的 Docker 从哪来

| 项 | 内容 |
| :--- | :--- |
| **需求出处** | `../归档/首版与第一部分改造/研究/2026-10-08-阶段讨论记录.md` 第 222、549、560、578 行 |
| **需求原文** | 第 549 行：「用户新增编程等复杂任务的 Agent 能力…**编程所需命令、测试、构建及开发工具执行纳入本次需求探究**」<br>第 560 行：「…以及本次补充的编程等复杂 Agent 任务。**具体工具、协议和运行环境第三阶段选择**」<br>第 578 行：「编程仍受指定工作区、文件范围和行动确认规则约束；**不因具有终端工具自动获得全机权限**」<br>第 222 行：「任务工作区、开发工具、结果验证与断点恢复（待验证）；**cwd 不等于进程隔离**」 |
| **需求到底要什么** | ① 编程任务要能真的跑命令和测试；② **但不能因为有终端就等于拿到全机权限**；③ **「运行环境」明确留给实现阶段选择** |
| **实现选了什么** | Docker Desktop + WSL2 + Linux 容器（`python:3.12-slim` / `node:24-bookworm-slim`） |
| **判断** | **方案固化**。需求只提了约束（不能拿全机权限），实现挑了最重的一种手段（完整容器隔离），然后这个手段的细节变成了项目的一部分。 |

### 2.3 现在的沙箱实际约束（`tools/docker.py`）

容器创建参数：非 root（65534）、根文件系统只读、丢弃全部 capabilities、`no-new-privileges`、默认 `--network none`、内存 256MB、1 CPU、进程数上限 64、超时限制、日志驱动关闭、`--pull never`（不联网拉镜像）、只挂载任务工作副本。

**需要记录的问题**：

- 镜像在组合根**硬编码**：`src/lingnexus/api/app.py` 第 98 行 `docker_image="python:3.12-slim"`，**没有环境变量可覆盖**，也没有设置项。
- 而 `src/lingnexus/tasks/README.md` 写的是 `docker_image=owner_configured_image, # optional, never model-selected`。**文档与实现不一致**——按文档你以为可配置，实际写死。

### 2.4 影响面

- 普通聊天、记忆、设置、备份、恢复**完全不需要 Docker**。
- Docker 只在「创建并执行编程任务」时被调用。
- 但要**用得上这个能力**，前置条件是：装 Docker Desktop + 开启 WSL2 + 预先拉好两个镜像。对"个人 Windows 首版"来说，这个前置成本很可能超过收益。

### 2.5 建议

1. **把沙箱变成可选项，而不是编程任务的前置条件。** 默认走"轻量受限执行"（限定授权目录、无 shell、超时与输出上限、进程/内存/CPU 上限），需要强隔离时再开 Docker。**不做命令白名单**（容易被解释器绕过，只是心理安慰）。
2. **把镜像从硬编码改成设置项**（或至少加环境变量），并修掉 README 与实现不一致的地方。
3. **不要删掉 Docker 沙箱。** 隔离强度本身是有价值的，只是不该是唯一路径。

→ 具体分层方案见 [`执行沙箱.md`](执行沙箱.md)。

**补充（2026-10-11，所有者追问"沙箱应该有多种实现形式吧"后核实）**：项目里其实**已经有半个沙箱的零件**，只是没接成一条路——
`tools/workspace.py`（授权分离、拒绝符号链接与父目录穿越、Windows 句柄级防替换、字节上限）、
`tools/_process.py`（`shell=False`、参数列表、超时、输出上限）、
`tasks/workspace.py`（单文件 1MB / 总量 32MB / 最多 2000 文件）。
但 `tools/_process.py` 这个本地进程原语**目前只被 `tools/docker.py` 和 `dependencies/driver.py` 使用**，也就是只用来调 docker CLI，从未暴露成本地执行器。**缺的只是包装，不是能力。**

### 逐条说明

**#1 分段阈值 —— 实现自加，但已隔离。**
需求第 522 行原文：「自动划分的助手工作默认：像日记章节一样组织连续交流，在合适的轮次间切分……
**具体时间间隔与主题识别方法第三阶段实测，不声称存在唯一最优阈值**」。
需求明确拒绝把"唯一阈值"写死，而实现里 `conversations/segments.py:56,61` 硬编码了 `0.15`（词重合度）与 `6 * 3600`（小时）。
**但该模块已列入第二部分禁区**（`tests/test_boundary_part1.py:34`），未在组合根装配——所以第一部分正在跑的行为不受它影响。**不在本次范围。**

**#2 后台让路 —— 需求要的。**
需求第 52 行：「交流优先、后台并行与暂停（工作默认）」。
实现 `background/supervisor.py:52` 先查 `foreground_busy()`、再查自己的锁，正是"交流优先"的直译。**保留。**

**#3 主备粘性 —— 需求要的；审计清单的原措辞不准确。**
原清单写的是"一次切换后不再切回主模型"，暗示这是隐藏状态。
需求第 279 行原文：「主模型暂时不可用时先通知，再自动切到用户预先指定的备用模型，无需等待再次确认；
**本次对话保持备用，下次开始对话优先使用主模型**」。
实现 `runtime/failover.py` 的绑定**按 `conversation_id` 存**（`chat_conversation_failover`，读 :120、写 :251），
即：**同一条对话内粘性、新对话自动回到主模型**——与需求逐字一致。**保留。**
（若要继续追问，真正该核的是"切换时有没有按需求先通知"，而非粘性本身。）

**#4 记忆召回 —— 实现自加，但已隔离。**
需求第 800 行：「不预设统一长度阈值」。实现 `context/recall.py:27` 有 `remaining=3200`、以及"最多 4 条"。
**该模块已列入第二部分禁区**（`test_boundary_part1.py:35`），仅被同样属禁区的 `activities/attention.py` 引用，未装配。**不在本次范围。**

**#5 上下文预算 —— 方案固化，且发现一处口径不一致。**
需求第 800 行只说"不预设统一长度阈值"，没给具体数字。给输出与工具结果留出空间是**工程必需**，
但 `256` 是经验值。更要紧的是**同一概念有两处不同默认**：
`context/builder.py:34` 的 `BudgetPolicy.tool_reserve` 默认 **4096**，而 `runtime/payload.py:54` 实际传 **256**。
聊天路径永远走 256，dataclass 的 4096 从未生效。这不是 bug（行为一致），但**两处口径不一会误导读者**。
建议：把这两个数字统一到一处并注明来由。

**#6 附件上限 —— 实现自加，但合理。**
需求文档里搜不到 25MB / 8MB / 12000 / 128 任何一个数字（概念"附件"只出现在交互要求里，未规定尺寸）。
实现分散在三处：`content/service.py:9`（单文件 25MB）、`content/extract.py:20`（PDF 单页 8MB）、
`runtime/attachments.py:18-19`（注入正文 12000 字节 / 128 段）+ `MAX_NATIVE_BYTES`（原生块 8MB）。
这些是防止一次请求撑爆上下文的必要上限，**保留**；但既属自加，应至少在此登记在案，日后若要调需知这是实现决定而非需求约束。

**#7 任务 40 步 —— 实现自加，已可配置。**
需求文档搜不到"40 步"。实现 `runtime/service.py:75-76`：`DEFAULT_MAX_STEPS = 40`，设置键 `chat.max_steps`（已支持 1 起自定义）。
**保留**：默认值是自加，但已可配置，且 C 阶段已把"预算用尽"如实报为 `step_budget_exhausted` 而非谎称完成。

**#8 备份保留 14 份 —— 实现自加，已可配置。**
需求文档搜不到"14"。实现 `maintenance/automatic.py:34` 默认 `retention: 14`，写入侧校验范围 1–365。
`docs/使用说明.md:82` 也如实写了"默认……保留 14 份"。**保留**：默认值是自加，但已可配置且文档已说明。

### 小结

- 8 条里 **2 条是需求要的**（#2 后台让路、#3 主备粘性），原清单把它们列为"来历不明"是**误判**，尤其 #3 的措辞与需求原文不符。
- **2 条属第二部分禁区**（#1 分段、#4 记忆召回），模块未装配，不构成第一部分的"来历不明限制"。
- **4 条是实现自加**（#5–#8），其中 **2 条已可配置**（#7 步数、#8 备份），**2 条是硬编码的安全上限**（#5 预算、#6 附件）。
- 唯一值得动手的是 **#5 的两处口径不一致**（4096 vs 256）——建议后续统一，其余登记在案即可，不必为"消除自加"而删掉合理的安全上限。
