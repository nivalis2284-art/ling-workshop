## 零、方针

**把项目拆成两大部分：**

| | 内容 | 状态 |
| :--- | :--- | :--- |
| **第一部分** | **一个可用且完善的 Agent 系统** | **唯一在跑的部分** |
| **第二部分** | 长期连续与发展、主动关注、多对话、Jev 等 | **整体隔离**，之后逐步加回 |

**核心目标**：先让第一部分作为 Agent 系统**合格**，把地基打牢；第二部分不参与运行，等梳理清楚后一条条加回来。

**三条拆分原则**：

1. **第一部分必须能独立运行且完整。** 缺了第二部分，它依然是一个能用的 Agent，而不是"残废版"。
2. **依赖方向单向。** 第二部分可以读第一部分的数据；**第一部分绝不能依赖第二部分**。
3. **边界只有一处。** 现在两侧完全不连通；将来加回时，也只允许在少数几个点上接触，不允许四处渗透。

## 一、第一部分：合格的 Agent 系统

### 1.1 什么叫"合格"

先把标准立出来，再对现状打分。一个合格的 Agent 系统，至少要满足下面这些：

| # | 合格标准 | 现状 | 结论 |
| :-- | :--- | :--- | :--- |
| 1 | 流式对话、可见思考、停止与重试 | 有 | ✅ |
| 2 | 编辑自己的消息、重新生成回复、删除一轮、分支切换 | 有 | ✅ |
| 3 | 文字、图片、常见文档输入 | 有 | ✅ |
| 4 | 多提供商、主备切换、多种协议原生适配 | 有 | ✅ |
| 5 | **对话内可以调用工具** | **明确不支持，模型一要求调工具本次就失败** | ❌ **缺** |
| 6 | **对话内多步循环**（计划→执行→观察→修正） | 只存在于独立的"任务"路径里，对话是一问一答 | ❌ **缺** |
| 7 | 中断与介入：暂停、恢复、中途补充指导 | 任务里有，对话里只有"停止生成" | ⚠️ 半个 |
| 8 | 安全执行：权限边界、重要操作确认 | 有，但**默认必须先装容器** | ⚠️ 门槛过高 |
| 9 | 状态、进度、真实用量可见 | 有 | ✅ |
| 10 | 对话历史留痕、可追溯 | 有 | ✅ |
| 11 | **默认不依赖任何外部引擎** | 编程任务依赖容器 | ❌ **缺** |
| 12 | 备份与恢复 | 有 | ✅ |
| 13 | 长对话的上下文处理 | 有，但**超预算就整条失败** | ⚠️ 需降级 |
| 14 | 安装简单 | 有安装包 | ✅ |

**得分：8 项合格，3 项半个，3 项缺失。**

**结论：它现在是一个"能说但不太能做"的系统。** 第 5、6、11 三条是必须补的，第 7、8、13 三条是必须收尾的。

### 1.2 第一部分要补的缺口

详细判断见 `docs/设计/2026-10-11-第一部分能力板块.md`。

| 缺口 | 目标 | 方向 |
| :--- | :--- | :--- |
| **对话内多步循环** | 对话即循环，模型可以连续多步行动直到完成 | 把已经存在于任务里的多步执行能力下沉为对话本身的能力 |
| **对话内调用工具** | 模型在对话中可以请求工具，系统执行并回传真实结果 | 把工具能力从"只在任务里可用"提升为对话的基本能力 |
| **工具集取向** | 工具"原子化" | **已确认：以低层原语为主**（命令、文件读写、文本编辑、搜索），自定义动作大幅精简。**工具不是越多越好** |
| **Hooks（策略注入）** | 机制与策略分离 | 把权限、审计、校验从循环里抽出来，通过钩子注入。**这是消除现有硬编码耦合的主要手段** |
| **上下文管理** | 长对话不再整条失败 | **已确认档位：只做"截断 + 明确提示"**——超出预算就丢掉最老的内容，并说明截了什么。压缩、摘要、落盘暂不做 |
| **默认零外部依赖** | 不装任何东西也能跑完整能力 | 执行沙箱分层：默认轻量受限执行，容器降为可选项 |
| **技能包（只读）** | 能加载外部给的能力说明书 | 按"文件夹 + 说明文件 + 三级渐进式披露"接入，零框架、零注册中心。**不含技能的自动积累** |
| **MCP 客户端（可选）** | 能连外部能力生态 | 只做最小集：连服务器、列工具、调工具、版本协商。**不配也能跑，不允许变成新的前置门槛** |

### 1.3 第一部分要收尾的三件事

| 项 | 现状 | 方向 |
| :--- | :--- | :--- |
| 中断与介入 | 只有"停止生成" | 让循环中的每一步都可被观察、中断、补充指导 |
| 执行门槛 | 必须先有容器引擎 | 默认档不依赖外部引擎；容器探测到才**提示**升级，不自动切 |
| 长对话处理 | 超预算整条失败 | 降级为"截断 + 明确提示"，并如实说明截了什么 |

### 1.4 第一部分保留的业务

对话与分支、附件理解、模型接入、工具与执行、权限与审批、状态与用量、备份与恢复、**系统指令**（所有者设定，不是自我演化）、**名字**（降为普通设置项）、**技能包（只读）**、**MCP 客户端（可选）**。

> **注意**：技能必须拆成两半。"技能作为能力包"（加载外部说明书）属于第一部分；"技能的自动积累与演化"（从经历里生成、版本、审批）属于第二部分。详见能力板块文档 2.3 节。

### 1.5 第一部分要处理的限制

| 限制 | 处置 |
| :--- | :--- |
| 落库前校验自我/记忆版本，不一致整条作废 | **随第二部分隔离一起消失** |
| 记忆被引用时禁止修改 | **随隔离消失** |
| 后台整理遇自我变化丢弃结果 | **随隔离消失** |
| 回忆条数与字节上限 | **随隔离消失** |
| 落库前校验附件摘要 | **直接删**（附件不可变，属假想敌） |
| 上下文超预算整条失败 | **降级为截断 + 提示** |
| 生成中禁用编辑/删除/重新生成 | **降级为允许，但明确提示后果** |
| 聊天不支持工具调用 | **第 5 条缺口要解决的正是它** |
| 备用模型对整条对话粘性且无提示 | **单独修**：自动切回主模型，或明确显示当前实际在用哪个 |
| 附件上限、任务步数上限、备份保留份数等常数 | **改成可配置**，并让文档与实现一致 |
| 落库时校验对话头未变 | **保留**（防你在生成时切分支，属基本正确性） |

## 二、第二部分：被隔离的内容

### 2.1 清单

| 类别 | 具体内容 |
| :--- | :--- |
| **长期连续与发展** | 原始经历库、事件卡与知识、记忆召回、自我状态与候选审批、后台整理、**技能的自动积累与演化**、长期目标、主题自动分段 |
| **主动关注** | 提醒、文件/网页/RSS 观察、关注事项回顾、授权内自主后续 |
| **多对话容器** | 界面入口已删，但后端仍保留"创建对话"的能力，一并隔离 |
| **Jev 辅助层** | 未配置、未验证、从不工作，整体隔离 |
| **情境（scope）残留** | 早期已决定移除，残留的字段、校验与文案彻底清掉 |
| **不做（与隔离不同）** | 内置计划清单、多 Agent 协作、子代理实现（先留接口） |
| **依赖它们的限制** | 版本校验、级联作废、反向阻塞等（见 1.5 前半段） |

### 2.2 数据怎么处理

- **一条都不删。** 经历、记忆、自我版本、候选、技能、目标原样留在原处。
- **不再读写。** 隔离期间不产生新数据，也不读取旧数据。
- **备份仍然包含它们**（整库备份）。这一点必须在界面上说明，否则你会以为数据丢了。

### 2.3 隔离方式（需要你选一个）

| 方案 | 做法 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| **一、运行时禁用** | 代码还在一起，只是启动时不加载 | 改动最小、回退最快 | 耦合还在代码里；第一部分仍"看得见"第二部分 |
| **二、模块边界 + 独立装配** | 两部分职责分明，之间只有一处边界；第一部分可独立装配与测试 | 耦合真正断开；第一部分能独立验证合格 | 需要一次结构性整理 |
| **三、拆成两个可发布单元** | 第一部分可单独发布/开源，第二部分作为扩展 | 最彻底，最利于开源 | 现在最重，会拖慢"打地基" |

**建议方案二。** 理由：方案一不够干净——耦合留在代码里，第一部分仍然会被牵动；方案三现在太重，会拖慢把地基打牢。方案二既能真正断开耦合，又保留将来切成方案三的路径（边界已经在了，切一刀就行）。

## 三、边界：两部分怎么接触

### 3.1 现在

**完全不连通。** 第一部分启动时不加载第二部分，不读它的数据，也不向它写数据。

### 3.2 将来加回时

只允许在三个点上接触，不允许四处渗透：

| 接触点 | 方向 | 说明 |
| :--- | :--- | :--- |
| 取上下文 | 第一部分 → 第二部分 | 组装本次对话时取长期资料 |
| 记录经历 | 第一部分 → 第二部分 | 对话产生新经历 |
| 校验与干预 | 第二部分 → 第一部分 | 长期资料变化时的处理 |

**关键约束**：这三个点全部是**可选的**——第二部分不在时，第一部分照常工作，只是少拿到一些资料、少记一些东西。

**接入方式**：这三个点**不应该再靠修改循环来接入**，而应该通过 Hooks 挂进去。这正是 Hooks 要在第一部分就做出来的原因之一——**它是将来加回第二部分的天然接口，也是防止耦合重新长出来的结构保证。**

### 3.3 依赖方向

**单向**：第二部分可以读第一部分的数据；第一部分绝不能依赖第二部分。

## 四、执行顺序

| 阶段 | 内容 | 前置 | 能否并行 |
| :--- | :--- | :--- | :--- |
| **A** | 划定边界、按**方案二**隔离第二部分、清理连带限制 | 无 | — |
| **B** | 执行沙箱分层：默认不依赖外部引擎 | **A 之后**（已确认先隔离） | 可与 C 并行 |
| **C** | 对话内工具调用 + 多步循环 + 中断介入；**任务合并进对话** | **A 必须完成** | — |
| **D** | 任务入口收进对话的收尾（旧任务路径去留、交互统一） | C | — |
| **E** | 长对话改为截断 + 提示、常数改可配置、文档与实现对齐 | 无 | **可与 A 并行** |
| **F** | 逐条加回第二部分的内容（由所有者梳理后决定） | A | — |

**关键路径：A → C。** 在 A 完成之前做 C，循环每跑一步都会被长期部分的耦合打断。E 随时可做，B 排在 A 之后。

## 五、明确不做

- 不删除任何长期数据。
- 不做 Linux 服务端 / Docker 部署（与"沙箱可选"是两件事，不要混）。
- 不改任务侧针对资料变化的强校验逻辑（隔离后自然失效，代码保留，将来加回时重新生效）。
- 不做多设备、音视频、图片生成。
- 不引入多 Agent 化（统一循环不等于创建多个灵）。

---

## 六、贯穿全程的要求

1. **A 完成后立刻留一个明确的恢复点**，任何时刻能退回到"第二部分还在"的状态。
2. **被隔离或删除的东西要留测试**，防止将来被无意中重新长出来。
3. **凡涉及数据安全的改动（备份、恢复），行为不许变。**
4. **文档与实现必须一致**——这一轮已查出多处不一致（镜像配置、任务步数、备份份数），一并修正。
5. **第一部分要能独立验收**：不启动第二部分的情况下，1.1 表里那 14 项全部达标。
