## 三、工作边界与顺序

经所有者批准，按 **A诊断及通信 → B恢复与部分交付 → C工作区规模及整体验收** 推进，确定性用例贯穿各批。先接入诊断再进行有界付费探针；已复现通道超时和终止ID更换，停止重复付费，B/C在隔离环境继续实现和验证。结构整理只随相关修改发生。

| 批次 | 当前交付与后续 |
|---|---|
| A | 结构化脱敏诊断接入两运行器，严格协议错误可定位；真实信息整理通过，但工具流仍更换ID。需要通道修复或获准采用另一付费方案，原始无trace错误仍unknown |
| B | 人工核对、保留unknown、放弃旧运行、持久逐文件记录、生成剩余审阅及再次确认写回已接入；真实本地界面闭环通过。未知进程不自动核销、不开放原地恢复 |
| C | 共用有界流式扫描、策略版本、统一排除范围、去重命令后扫描已接入；规模测量有证据；通用探针只实现信息整理/文件/多工具三类，完整五类真实矩阵未完成 |

具体数值、命令、费用、来源及未测范围统一见[当前审查](../审查记录/审查.md)，不将工程实现等同阶段验收通过。

### A：先让故障可定位，再修通信（P0）

1. 冻结本轮源码、评测控制器、夹具和资源参数；将已有20次尝试按产品/协议边界/控制器/模型未完成/证据不足分类。先回放现有脱敏响应，不立即补新旧整套付费对照。
2. 在两种运行器异常边界记录错误关联ID、阶段、异常类型和项目内栈位置；可复用`evaluate_coding.py::_safe_exception_diagnostic`的思想，但不让产品运行时反向依赖评测脚本。默认不记录异常消息、局部变量、请求头、原生块或完整路径。错误码与前端提示保持稳定、可关联。
3. 为解析失败保留结构化原因（如流标识变化、缺终止事件），不把不透明原生内容公开。原始流如需采集，只能在显式诊断模式下有界脱敏存储并验证密钥不落盘。
4. 对已有task_runtime_error先用相同原生响应、工具结果和边界故障注入复现；能定位的补最小失败回归再修。早期无trace无法复原时保留unknown，当前源码若无法复现则登记证据限制，不无限循环追查旧现场。
5. 检查通道是否能修复，或以稳定链路做小规模验证。保留响应ID、调用ID、工具参数及完整终止校验；不合并不同响应的工具片段、不自动执行未完成流中的工具。
6. 梳理现有聊天主备切换策略（主要限首步、最多一次切换）与任务失败处理。只有完整请求状态可重发、没有待核对副作用的模型请求才考虑有界重试；先建议最多额外1次，限瞬时网络/限流/服务不可用，退避且每次独立记账。malformed、拒绝、无效参数、上下文超限直接停并说明处理方法；不重放外部工具。

影响模块：`models/_parsers.py`、`models/gateway.py`、`runtime/service.py`与`failover.py`、`tasks/service.py`与`protocol.py`、对应错误展示和评测采集。

验收：已有错误响应离线回放仍安全拒绝；每次失败能关联到模型请求/解析/工具/持久化/控制器阶段；未知副作用计数不增加；正常流完成并实际续接工具结果。出现同类协议错误后停止该链路批量付费，转回诊断。真实流探针待模型、链路及预算确认。

### B：补全核对、恢复与剩余交付（P0/P1）

1. 统一展示阻塞原因与证据入口：会话、命令说明、输出/时间、相关工作区、工具效果、逐文件前后hash和原始内容；敏感命令参数不能直接从私有记录全量公开。
2. 设计最小持久化核对记录：核对对象和版本、操作者、时间、证据及结论。结论区分“系统已确认”“所有者人工判断”“仍无法确认”；原unknown事实不可被覆盖成执行成功。
3. 已有明确结果只补回填或引用，不重跑；未知命令若无可靠进程/容器身份，不凭PID认领或终止。不能证明停止时保持原工作区恢复/写回阻断，提供下载已知材料、放弃旧运行、在独立副本重新开始的明确路径。
4. 人工确认只处理可核对的业务结果，不伪造`cleanup_confirmed`。仅在进程状态、安全围栏、权限、分支和版本重新验证都满足时才开放原运行继续；若现阶段无法安全核销某类unknown，提供可用的退出路径并明示限制即可。
5. 对部分写回增加核对/生成新审阅流程：已应用内容须仍等于记录after hash，未应用项须仍等于before hash；不满足则逐文件列冲突，交由用户审阅新差异。新审阅只包含剩余文件，不自动重试旧review；已应用结果不撤销。遇到unknown先核对实际内容及执行来源，再允许后续步骤。
6. 后端、API与聊天/任务界面同时交付。重复点击、并发核对、请求失败后重试须幂等；所有入口受owner认证、归属、当前授权与状态版本校验约束。需要新表时递增迁移，不重写029/030。

影响模块：`tools/sessions.py`、`tasks/sandbox.py`、`runtime/checkpoints.py`、两个运行器、`tasks/workspace.py`和store、`api/execution.py`及chat/tasks路由、聊天控制和任务详情。

验收：真实延迟写命令覆盖页面断线、暂停、正常退出、进程重启、清理unknown；确认不会重复副作用。两文件应用第二项失败后可定位成功/未应用/冲突并安全处理剩余项；权限撤回、内容变化、再次重启、重复核对均不会绕过闸门。人工判断与程序确认在API和界面可区分。

### C：按测量结果改善规模，并完成通用任务验收（P1）

1. 拆开测量指纹、快照复制、差异审阅、应用前校验、每轮检查点成本；用100/2000/10000文件及小于/大于32MiB、含大文件/依赖目录/链接/不可读项的固定生成数据，记录机器与冷/热扫描时长、读入量、峰值内存。先测量，再确定本轮支持包络。
2. 统一显式扫描策略与失败原因：文件数量、单文件/总字节、目录项、时间/权限/链接限制；指纹与副本有不同用途，但覆盖范围必须可见并纳入版本。不能把未扫描内容当作相等，改变排除规则使旧证据失效。
3. 优先实现流式安全hash、manifest复用和同一稳定边界内的重复扫描消除，减少全量内容驻内存。修改目标在写入前仍做内容版本检查；任意外部命令或不受控外部修改后保留重新校验，不能只信mtime/size或文件监控缓存。
4. 如整个目录过大，可允许所有者显式选择任务子目录/文件集并展示覆盖范围；不静默忽略文件。快照单文件读取上限与工具文本返回上限分别处理，不以无限放大资源额度替代优化。初版不建设长期索引服务或复杂文件监控系统。
5. 建议首轮目标：至少覆盖10000个小文件、64MiB纳入内容及单个8MiB文件的指纹与副本流程（文本工具输出仍有界），峰值内存受配置约束；相同2000文件夹具的重复完整hash次数至少减半。绝对时延SLO在第1步测量后写入验收记录，若本机成本超出可接受范围，收敛为明确子目录支持而非继续扩张。
6. 在A/B改动中按职责抽出诊断记录、恢复判定、扫描策略；前端可分离事件更新与恢复控制，但以减少重复状态分支、测试边界清晰为收益证据。原有消息/分支/确认/停止/设置行为必须回归。

验收：包络内任务创建、修改、审阅、恢复、交付均可完成；包络外返回明确可操作原因；版本未知仍阻断。大目录中的权限撤回、链接替换、同大小内容变化和最终写入冲突不能漏检。保留跨进程最终rename前窗口的真实边界，不宣称强CAS。

## 四、通用 Agent 验收设计

经批准的通用 Agent 验收设计：用“确定性故障回归 + 实际运行器真实任务 + 所有者体验”三层验证，不把自动测试替代真实体验，不把工具退出0或关键词匹配当作语义成功。

固定10个真实场景（五类各2个），通过当前产品接口运行，覆盖普通对话与独立任务，而非全部经task运行器：

| 类别 | 场景与完成依据 |
|---|---|
| 问答/信息整理 | 多轮约束问答；从受控网页收集信息并输出带来源整理。对照已知事实、来源可访问性、遗漏及不确定表述；无需为了verified跑命令 |
| 文件/本地资料 | 多份文本资料整理成可回读清单；受控多文件修改中途制造冲突。核对内容、源文件保护和逐文件状态。Office/PDF如缺依赖列不支持，不纳入首轮硬门槛 |
| 浏览器 | 受控站点跨页查找；填写后由所有者批准提交并回读结果。核对来源授权、page_version、审批、实际结果及重复提交计数；禁止对真实账号产生测试副作用 |
| 编程 | 简单修错；中等跨文件功能。复用已有六类夹具中两类，用独立验收器判断成品；全部六类离线正反夹具继续回归 |
| 持续执行/多工具 | 文件→命令→回读；长命令中断→核对→安全继续或明确退出。以真实状态、输出和副作用计数验收 |

模型执行矩阵：主链路10场景各1次；有状态高风险4场景再各2次，共18次。预算不足时分批，不能把只做冒烟写成完整矩阵通过。三协议继续合成回归，真实阶段只承诺指定链路（产品评测优先既有 glm-5.3-flash 链路；评测时机与通道由 Codex 自主选择），不要求同时购入三家服务。

每次记录：源码/控制器/夹具版本、模型与协议、配置及资源、链路标识、结果证据、人工介入、耗时、已知/缺失用量、费用预留、失败分类。分别报告目标完成率、框架故障、模型未完成、正确安全阻断及未测项；安全阻断不算业务完成，也不算安全缺陷。

发布门槛（经批准）：确定性安全回归全部通过；真实矩阵零未授权操作、零重复副作用、零静默覆盖、零虚假验证；正常路径10场景至少9个目标达成，剩余有明确原因；涉及恢复/写回/审批的场景若仍有安全缺陷，即使总体达标也不通过。18次只作为工程验收，不声称有统计意义的稳定成功率。所有者体验单独登记。

检查命令：相关专项按每批执行；最终后端全量pytest、ruff，Node24下前端typecheck/test/build，`start.bat`真实启动与交互走查，文档链接检查。容器及Windows链接测试按环境如实标注，不以跳过代替通过。
