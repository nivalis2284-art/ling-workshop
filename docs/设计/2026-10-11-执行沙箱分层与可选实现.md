## 一、现状：为什么变成了"一定 Docker"

溯源见审计 #2。摘其要点：

- 需求只说了一句约束：「**不因具有终端工具自动获得全机权限**」（研究记录第 578 行）；
- 需求同时明确把「**运行环境第三阶段选择**」留给实现（第 560 行）；
- 需求还留了一句提示：「任务工作区…**cwd 不等于进程隔离**」（第 222 行）。

实现阶段直接选了最强的手段——Docker Desktop + WSL2 完整容器隔离。**没有对其他手段做过比较，也没有做分层。**

结果（`src/lingnexus/tasks/execution.py` 第 243 行附近）：

```
if not task["workspace"] or not task["docker_image"]:
    raise PermissionDenied("Command requires an authorized snapshot and configured image.")
```

`run_command` **硬性要求**有工作副本和已配置镜像，唯一执行者是 `DockerExecutor`。**没有 Docker，编程任务一步都跑不了。**

## 二、必须先分清的两件事：防手滑 vs 防敌意

这是整个设计的分水岭，也是"为什么不一定需要 Docker"的答案。

| | 防手滑（误伤） | 防敌意（恶意） |
| :--- | :--- | :--- |
| 防的是什么 | 模型理解错了、命令写错了，顺手删了你的文件 / 装了一堆东西 / 改了系统 | 模型被提示注入攻击（比如网页里藏了指令），主动去偷密钥、外传数据、装后门 |
| 典型手段 | 目录授权、无 shell、参数列表、超时、输出上限、命令白名单、进程/内存上限 | 容器、轻量虚拟机、云端沙箱、专用低权限账户 |
| 强度 | 弱—中 | 强 |
| 前置成本 | **接近零** | 高（要装引擎 / 建账号 / 联网） |
| 覆盖多少真实场景 | **绝大多数** | 少数高风险场景 |

**关键判断**：如果你用的模型渠道是你自己配的官方服务，且任务输入主要来自你自己，那么**你需要的几乎只是"防手滑"**。Docker 防的那个"敌意"，在当前使用方式下出现的概率极低——**这又是一个"假想敌"**。

但这不等于不需要容器：一旦开放网页操作、外部资料进入上下文，"敌意"就有了入口。所以**容器应该保留，只是不该是默认**。

## 三、候选手段对比

按"个人 Windows 首版 + 未来开源"两个前提评估。

| # | 手段 | 隔离强度 | 前置成本 | 跨平台 | 实现成本 | 定位 |
| :-- | :--- | :--- | :--- | :--- | :--- | :--- |
| A | 直接执行（无隔离） | 无 | 0 | ✅ | 0 | ❌ 不可用 |
| B | **目录授权 + 无 shell + 超时/输出上限** | 弱—中 | **0** | ✅ | **低（零件已有）** | ✅ **默认** |
| C | B + **命令白名单** | 中 | 0 | ✅ | 低 | ✅ 默认增强 |
| D | C + **Windows 作业对象**（限制内存/CPU/进程数，退出时杀进程树） | 中 | 0 | ⚠️ Windows 特化 | 中 | ✅ Windows 默认增强 |
| E | **容器**（Docker / Podman） | 强 | **高** | ✅（需引擎） | 中（**已实现**） | ✅ 可选 |
| F | 轻量虚拟机 / WSL2 直用 | 强 | 高 | ⚠️ | 高 | 可选 |
| G | **云沙箱**（E2B 等） | 强 | 中（账号+联网） | ✅ | 中 | 可选，插件 |
| H | **只产出补丁，不执行** | 无（但零风险） | 0 | ✅ | 低 | ✅ 兜底降级 |

> 注：`macOS sandbox-exec`、`Linux firejail/bubblewrap/nsjail` 属于 E/F 那一档，可留给插件实现。

## 四、分层设计

### 4.1 四档能力，自动降级

> **已确认：默认档 = 第 2 档；不做命令白名单。**

| 档 | 名称 | 组成 | 何时启用 |
| :-- | :--- | :--- | :--- |
| **第 1 档** | 目录受限执行 | 只动授权目录、无 shell、参数列表、超时、输出上限 | 永远可用（零件已有） |
| **第 2 档** | 加资源限制 | 第 1 档 + 进程/内存/CPU 上限 | **默认档** |
| **第 3 档** | 容器隔离 | Docker / Podman | 探测到引擎时**提示可升级**，不自动切 |
| **第 4 档** | 云沙箱 / 轻量虚拟机 | 外部服务或额外环境 | 插件式，需要时再接 |

> **不做命令白名单**：它很容易被解释器绕过（一条命令就能执行任意代码），做了只是心理安慰，反而多一层要维护的限制。

**行为约定**：

- 没有 Docker → 自动落在第 2 档，**编程任务照常可用**，不再报 `PermissionDenied`。
- 探测到 Docker → 界面上给一个"可升级到容器隔离"的提示，由你决定是否切换。
- 任何一档都保留"只产出补丁不执行"的降级出口。

### 4.2 隔离等级必须对用户可见

按项目"无黑盒"的一贯风格，**当前处在哪一档要显示出来**，并且要诚实描述它防得住什么、防不住什么。

例如：

> 当前执行方式：**目录受限 + 资源限制**（未使用容器隔离）
> 它能防：误删授权目录外的文件、失控进程占满内存、命令无限输出。
> 它**不能**防：模型被恶意指令诱导后主动外传数据。需要后者请开启容器隔离。

**不能**在只做路径校验的情况下宣称"已隔离"——那是虚假安全感。

### 4.3 架构：接缝 + 多实现

沿用与 `ContinuityPort` 相同的手法（见隔离计划第四节）：定义一个执行端口，多个实现。

```
ExecutionSandbox
├── available() -> SandboxInfo          # 本机可用哪一档
├── execute(argv, *, cwd, writable) -> ExecutionResult
└── describe() -> 面向用户的隔离等级说明

实现：
├── RestrictedLocalSandbox   （第 1/2 档，默认）
├── ContainerSandbox         （第 3 档，包一层现有 DockerExecutor）
└── (插件位)                  （第 4 档）
```

`tasks/execution.py` 里那段硬编码的 `DockerExecutor(...)` 改成向端口要一个执行器。

## 五、可以复用的现成零件（不需要新写）

项目里**已经有一半的零件**，只是没接成一条路：

| 零件 | 位置 | 已经做了什么 |
| :--- | :--- | :--- |
| 受限文件工具 | `tools/workspace.py` | 读/写授权分离、拒绝父目录穿越、拒绝符号链接/硬链接/ADS/保留名、Windows 上句柄级防替换、字节上限 |
| 受限进程原语 | `tools/_process.py` | `shell=False`、参数列表、超时、输出上限、分块排空 |
| 工作区边界 | `tasks/workspace.py` | 单文件 1MB、总量 32MB、最多 2000 个文件 |
| 容器执行器 | `tools/docker.py` | 第 3 档的完整实现（已可用） |
| 任务快照 | `tasks/` | 任务跑在工作副本上，不碰原项目 |

**缺的只是**：把 `_process.py` 的进程原语包装成"第 1/2 档执行器"，并在 `run_command` 里做一次选择。

## 六、开源角度的额外要求

既然要开源，有三条是硬要求：

1. **默认零外部依赖。** 克隆下来就能跑，不能要求先装 Docker Desktop。这条直接决定别人会不会继续用。
2. **沙箱插件化。** 别人可能想接自己的沙箱（Linux 上 bubblewrap、macOS 上 sandbox-exec、云端 E2B）。端口式设计天然支持。
3. **诚实声明隔离等级。** 开源项目最忌讳"宣称安全但实际只是路径校验"。宁可写得保守。
