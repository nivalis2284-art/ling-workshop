# 里程碑与阶段拆分

## 里程碑是什么

一个能独立说清「完成了什么、验收口径是什么」的大块工作。判断标准：完成后能写出一句「本项目现在可以 ___ 了」。

- 不够格当里程碑的：零碎整理、文档修订、探索调研——这些是日常工作，不套里程碑流程（不出计划 / 执行 / 审查三件套）。
- 里程碑命名：`M#-短名`，序号递进；当前进度看 [`../03-路线图/00-README.md`](../03-路线图/00-README.md)。

## 阶段拆分四原则

1. **垂直切片优先**：每个阶段交付一条完整可验证的能力路径。
   为什么：水平分层（先做完所有模型、再做所有接口）会让「半成品」堆积很久，无法验收。
2. **每阶段可独立验收**：阶段结束时能跑出证据（测试通过 / 功能实测）。
   为什么：不可验收的阶段无法判断「做完没有」，只会无限拖延。
3. **依赖显式**：阶段表写清前置；隐晦的依赖会让人排错顺序。
4. **粒度适中**：一个阶段以 3–7 件能独立说清的事为宜；过大先拆，过小可合并。
   为什么：粒度过大 → 计划失控、上下文爆满；过小 → 流程成本超过工作本身。

## 目标倒推法（写计划前必做）

从「完成时什么必须为真」倒推，而不是从「要做什么」正推：

1. **truths**（可观察的事实）：完成后外界能观察到什么？列出 3–7 条。
2. **artifacts**（必须存在的产物）：哪些文件 / 功能 / 文档必须就位？
3. **key_links**（必须接通的连线）：产物之间必须怎样连接？（组件 → 接口 → 数据）

为什么：正推产生「任务清单」，倒推产生「验收标准」——任务清单回答不了「怎么算做完」。

## 调研深度分级

动手前先定这次需要查多深，避免「要么不查乱搞、要么过度研究」：

| 级别 | 场景 | 动作 |
|---|---|---|
| 0 跳过 | 完全沿用现有代码模式，无新依赖 | 直接干 |
| 1 快查 | 已知库的语法 / 版本确认，低风险可改回 | 查文档，不写报告 |
| 2 标准 | 2–3 个方案比较、新外部集成、中风险 | 调研并记录结论 |
| 3 深挖 | 架构级决策、难回退、无先例 | 完整调研，结论进计划「依据」节 |

## 反模式

| 反模式 | 为什么是问题 |
|---|---|
| 阶段粒度过大（一个阶段含十件事） | 计划写不清，执行到一半发现漏了 |
| 靠「默契」依赖（没写前置但实际有） | 执行时才发现顺序错了，返工 |
| 把「想做」写成「必做」 | 未来 Agent 当成铁律，不敢调整 |
| 不设验收口径 | 「做完了」永远说不清 |
