# 执行记录与审查记录写法

## 执行记录（[`../05-执行记录/`](../05-执行记录/00-README.md)）

四节，缺一不可：

| 节 | 要求 | 为什么 |
|---|---|---|
| 实际改动 | 按文件 / 模块列 | 与计划的「改什么」对照 |
| 验证与结果 | **贴命令与实际输出** | 「已通过」不是证据，输出才是 |
| 偏离计划之处与原因 | 必填，没有就写「无」 | 偏离不记录，计划与现实脱节 |
| 遗留问题 | 显式列出 | 防止「好像做完了」的幻觉 |

## 审查记录（[`../06-审查记录/`](../06-审查记录/00-README.md)）

结构：验收项逐条对照（带证据列）→ 发现的问题（分级）→ 结论 → 回退点。

问题分级：**阻断**（不修不能收）/ **一般**（该修，可带着走）/ **建议**（可选）。

## 三级验证（审查的核心方法）

对每个「已完成」的声明，逐级问：

1. **存在**：文件 / 功能真的在吗？（不是只在计划里）
2. **实质**：是真实现，不是存根？（TODO / placeholder / 空函数 = 存根）
3. **接线**：真的被调用 / 被装配了吗？（建了文件没导入 = 没接线）

为什么：「文件建了」「测试跑了」「接口写好了」是三回事——绝大多数「做完了但没生效」的问题死在第 3 级。

## 存根检测模式

审查时主动搜：TODO / FIXME / placeholder / `return null` / 空处理器 / 「coming soon」。命中即降级为「未完成」并登记。

## 证据要求

| 变更类型 | 需要的证据 |
|---|---|
| 测试 | 测试运行输出（通过数 / 失败数） |
| 构建 | 构建命令输出 |
| 界面 | 实测说明（谁、在什么页面、看到什么） |
| 数据 | 查询结果 |
| 文档 | 无——但要有对应改动的记录 |

为什么：没有证据的「完成」是愿望；与 AGENTS.md「诚实与证据」同源。

## 反模式

| 反模式 | 为什么是问题 |
|---|---|
| 审查写「看起来没问题」 | 审查沦为签字 |
| 执行记录不贴输出 | 无法复现「当时真的过了」 |
| 偏离不记录 | 计划与现实悄悄脱节 |
| 只测开心路径 | 删掉实现还能过的测试不是测试 |
